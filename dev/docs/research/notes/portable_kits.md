# Portable agent kits: packaging, distribution and sync across tools (as of 10 Nov 2026)

Method note: star counts, release dates and file contents were read directly from GitHub via `gh api` on 2026-11-10 (read-only). Claude Code behaviour is taken from code.claude.com docs fetched the same day. Blog and comparison pages are secondary and flagged as such. Star counts in this ecosystem are very large and some are probably inflated by bots or trending effects; treat them as popularity signals only.

## 1. What are the leading kits and what does each actually ship?

### Takeaway
The kits sit at different layers: Superpowers and Compound Engineering (CE) are skill plugins that impose an execution method; Spec Kit, OpenSpec, BMAD and Agent OS are spec or standards scaffolding delivered by a CLI or installer that writes files into the project. Almost all now ship to many agent hosts (Superpowers and CE to 14-16), and the trend is toward fewer files and lighter process (Agent OS v3 dropped most of its own workflow; Superpowers 7.x trims brainstorming questions). For a designer/consultant, the relevant ones are Superpowers (a plugin, no scaffolding) and OpenSpec/Agent OS-style ideas (project-level standards and a small config file), not BMAD or Spec Kit's full ceremony.

**Superpowers (Jesse Vincent / Prime Radiant)**

- Install on Claude Code: `/plugin install superpowers@claude-plugins-official` (official marketplace) or `/plugin marketplace add obra/superpowers-marketplace` then `/plugin install superpowers@superpowers-marketplace`. - Other hosts: Codex app/CLI via the official Codex plugin marketplace, Cursor `/add-plugin superpowers`, Copilot CLI `copilot plugin marketplace add obra/superpowers-marketplace`, OpenCode by telling the agent to fetch an INSTALL.md, Gemini `gemini extensions install` — [README](https://github.com/obra/superpowers)
- Anonymous version telemetry exists via a logo loaded from the maintainers' site in the optional visual companion; opt out with `SUPERPOWERS_DISABLE_TELEMETRY` or Claude Code's `DISABLE_TELEMETRY` — [README](https://github.com/obra/superpowers)
- Maintainers do not generally accept new skills and refuse agent-written PRs for other people's issues — [README](https://github.com/obra/superpowers)
- 7.0.0 (2026-10-09) rebuilt brainstorming; 7.0.1 and 7.0.2 retuned it after users said the new questions "got annoying fast and felt formulaic"; the project reports blind-graded filler questions dropping from 41 to 23 — [release notes](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)

**Compound Engineering plugin (Every; Kieran Klaassen, Trevin Chow)**
- Core idea: a loop of brainstorm, plan, work, simplify, review, then compound (write learnings into `docs/solutions/` so the next plan reads them). "80% is in planning and review, 20% is in execution" — [README](https://github.com/EveryInc/compound-engineering-plugin)

**GitHub Spec Kit**
- Core idea: spec-driven development; now framed as "choose your process" (SDD in core; bug-fixing and idea assessment as bundled extensions). SDD commands: constitution, specify, plan, tasks, implement, converge — [README](https://github.com/github/spec-kit)
- Mechanisms: integrations (per agent), extensions, presets (override templates/terminology/standards), workflows, bundles, catalogs (community and private), project-local overrides — [README](https://github.com/github/spec-kit)
- Install: `uv tool install specify-cli` then `specify init my-project --integration copilot`; needs Python 3.11+ and uv. Upgrade is two-part: `specify self upgrade` for the CLI, then `specify integration upgrade <key>` and `specify extension update` for project files. Repeating `uv tool install` does not upgrade — [README](https://github.com/github/spec-kit), [upgrade guide](https://github.com/github/spec-kit/blob/main/docs/upgrade.md)
- Mixed-agent teams are told to init with `--integration none` and each developer runs `specify integration switch <key>` locally, then switch back to `none` before committing; "Do not manually edit Spec Kit-generated agent commands or skills" — [integrations doc](https://github.com/github/spec-kit/blob/main/docs/integrations/index.md)
- Martin Fowler's site (Birgitta Böckeler) found Spec Kit overkill for a 3-5 point feature, verbose and repetitive to review, the constitution applied too eagerly, and the agent still duplicated existing classes despite the research step — [martinfowler.com](https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)

**Agent OS (Builder Methods, Brian Casel)**
- v3.0 (2026-01-20) deliberately shrank scope: it now focuses on standards (`/discover-standards`, `/inject-standards`, an `index.yml`, `/shape-spec` on top of plan mode) and retired its own spec, task-breakdown and orchestration phases because "Claude Code's plan mode... now handle[s] much of the scaffolding" — [CHANGELOG](https://github.com/buildermethods/agent-os/blob/main/CHANGELOG.md)

Unreleased fixes were for silent install failures under `set -e` and GNU-only `tac` on macOS — [config.yml](https://github.com/buildermethods/agent-os/blob/main/config.yml), [CHANGELOG](https://github.com/buildermethods/agent-os/blob/main/CHANGELOG.md)
- Closest conceptual match to the reader's "own kit plus thin per-project template" design (base profile, per-project copy, sync back), but it is script-based, not a plugin, and low activity since January.

### Inferences
- Superpowers is the only major kit that is purely a plugin with no project scaffolding, which matches the reader's intended use (enable by default next to own skills) and is the cheapest to adopt; its measured overhead in the one independent benchmark was about 10% cost.
- CE, BMAD and Spec Kit bring heavy per-project artifacts (docs/plans, docs/solutions, `_bmad/`, `.specify/`) aimed at software teams; for documentation and design work, copy ideas (compound-learning capture, config.yaml with `docs_root`, constitution-like standards file) instead of installing them.
- Agent OS v3's own changelog is evidence that frontier models and Claude Code's native plan mode absorb orchestration; kit value is shifting to standards, domain knowledge and guardrails, which is what a designer's kit mostly is.
- Star counts vary wildly between plausible-sounding projects (ECC 300k, gstack 141k); I could not verify organic growth, so do not use stars to rank quality.

### Gaps
- I did not read Agent OS's actual install docs (buildermethods.com) or BMAD's `_bmad/custom` customisation docs; only the READMEs, changelog and config.
- No verified Hacker News or Reddit threads were retrieved; web search returned mostly SEO comparison pages and a few Medium-type articles. Community sentiment here rests on GitHub issues and the Surge benchmark.
- ECC, gstack, oh-my-claudecode: I read only the top of READMEs (gstack) or repo descriptions (others); their internals and criticisms are not assessed.

## 2. How do Claude Code plugins work as a distribution unit in 2026?

### Takeaway
A plugin is a folder with an optional `.claude-plugin/plugin.json` plus default directories for skills, commands, agents, hooks, MCP, LSP, output styles, workflows, monitors, `bin/` and a limited `settings.json`; a marketplace is a git repo with `.claude-plugin/marketplace.json`. Private GitHub marketplaces work using the user's own git credentials, auto-update is off by default for third-party marketplaces, and a plugin cannot ship CLAUDE.md or rules; instructions must be written as skills (or injected by a SessionStart hook, which is how Superpowers does it).

### Cited Findings

**Structure and manifest**
- Manifest is optional; only `name` is required. Components load from standard locations: `skills/`, `commands/` (older; "prefer skills/ for new plugins"), `agents/`, `hooks/hooks.json`, `.mcp.json`, `.lsp.json`, `output-styles/`, `workflows/`, `themes/`, `monitors/monitors.json`, `bin/`, `settings.json` — [manifest reference](https://code.claude.com/docs/en/plugins-reference)
- Every component is namespaced under the plugin name: skill `/plugin:skill`, agent `plugin:agent`, MCP server `plugin:name:server` — [manifest reference](https://code.claude.com/docs/en/plugins-reference), [components](https://code.claude.com/docs/en/plugins/components.md)
- Names starting with `claude-`, `anthropic-`, `cc-plugin-` or that put "official" beside claude/anthropic are rejected by `claude plugin validate` (a warning if "claude" appears as a whole word elsewhere) — [manifest reference](https://code.claude.com/docs/en/plugins-reference)
- `defaultEnabled` (default true) decides whether a plugin starts enabled when the user has not set it; once a user's `enabledPlugins` entry is written it persists across updates — [manifest reference](https://code.claude.com/docs/en/plugins-reference)
- `userConfig` lets a plugin prompt for values (string, number, boolean, directory, file; `sensitive` values go to the secure credential store); values are available as `${user_config.KEY}` in MCP/LSP config, exec-form hook args, and non-sensitive in skill/agent content, and as `CLAUDE_PLUGIN_OPTION_<KEY>` env vars in hooks. `claude plugin install` never prompts; use `--config KEY=VALUE` — [manifest reference](https://code.claude.com/docs/en/plugins-reference), [components](https://code.claude.com/docs/en/plugins/components.md)
- `dependencies` lets one plugin require others (`name`, `name@marketplace`, or object with version range); a bundle plugin in `enabledPlugins` can roll out a set — [manifest reference](https://code.claude.com/docs/en/plugins-reference), [org docs](https://code.claude.com/docs/en/plugins/org.md)
- Variables: `${CLAUDE_PLUGIN_ROOT}` (per-version install dir, changes on update, do not write state), `${CLAUDE_PLUGIN_DATA}` (`~/.claude/plugins/data/<id>/`, survives updates), `${CLAUDE_PROJECT_DIR}` — [manifest reference](https://code.claude.com/docs/en/plugins-reference)
- Skill frontmatter in plugins: `description`+`when_to_use` listing text is truncated at 1,536 characters; `disable-model-invocation: true` removes the description from context and makes the skill user-only; `user-invocable: false` hides it from the `/` menu; `paths` limits auto-activation to matching files — [skills docs](https://code.claude.com/docs/en/skills)
- Plugin agents cannot use `permissionMode`, `hooks`, `mcpServers` or `initialPrompt` frontmatter (ignored); hooks and MCP must be declared at plugin level — [components](https://code.claude.com/docs/en/plugins/components.md)
- Plugin `settings.json` only honours `agent` and `subagentStatusLine`; all other keys (permissions, env, etc.) are dropped, and a user's own setting overrides it — [components](https://code.claude.com/docs/en/plugins/components.md)
- Hook gotcha: if two enabled plugins share a manifest name, only one registers its `hooks/hooks.json` hooks — [loading reference](https://code.claude.com/docs/en/plugins/loading.md)
- Windows: substituted paths use forward slashes except in exec-form or PowerShell hooks; backslashes in component paths in a manifest only load on Windows; PowerShell is the default hook shell when Git Bash is absent — [manifest reference](https://code.claude.com/docs/en/plugins-reference)
- Executables in a top-level `bin/` go on the Bash tool PATH but claude.ai/Cowork reject plugins with that directory — [manifest reference](https://code.claude.com/docs/en/plugins-reference)
- Validation: `claude plugin validate ./plugin` (and for a marketplace); `--strict` turns warnings into failures for CI. Plugin evals exist (`claude plugin eval`) — [manifest reference](https://code.claude.com/docs/en/plugins-reference), used in practice in [Superpowers issue 2386](https://github.com/obra/superpowers/issues/2386)

**What a plugin cannot do**
- "A `CLAUDE.md` at the plugin root isn't loaded as context, and `claude plugin validate` warns when it finds one. To include instructions that load into Claude's context, put them in a skill." — [manifest reference](https://code.claude.com/docs/en/plugins-reference); same in [components](https://code.claude.com/docs/en/plugins/components.md)
- A plugin also cannot ship permission rules or env (only `agent` and `subagentStatusLine` settings take effect), cannot make project files (no scaffolding command beyond what a skill/script does), and agents inside plugins cannot carry hooks or MCP — [components](https://code.claude.com/docs/en/plugins/components.md)
- A plugin cannot read `${user_config}` in shell-form hooks, monitors or `headersHelper` for security reasons — [manifest reference](https://code.claude.com/docs/en/plugins-reference)
- A repo-shared plugin's monitors do not load and MCP bundles from outside the plugin dir are skipped — [loading reference](https://code.claude.com/docs/en/plugins/loading.md)

**Marketplaces**
- A marketplace is a directory/repo with `.claude-plugin/marketplace.json` (required `name`, `owner`, `plugins`); each entry needs `name` and `source` (relative path, `github`, `git-subdir`, `url`, `archive`, `npm`, `command`); keep entry name equal to the plugin.json name; one user cannot have two marketplaces with the same name, so pick a distinctive name — [create a marketplace](https://code.claude.com/docs/en/plugin-marketplaces)
- Local relative-path marketplace added from a folder loads plugin files in place; edits apply at next session start or `/reload-plugins` with no version bump — [loading reference](https://code.claude.com/docs/en/plugins/loading.md)
- Symlinks inside a plugin: kept if they point within the plugin, dereferenced (copied) if they point elsewhere in the same marketplace, skipped if outside it. This allows a single repo to hold shared skills used by several plugins — [host a marketplace](https://code.claude.com/docs/en/plugins/host-marketplace.md)
- Do not keep needed files in Git LFS (clones get pointer files) — [host a marketplace](https://code.claude.com/docs/en/plugins/host-marketplace.md)
- Renaming: a plugin `name` is its identifier and appears in `enabledPlugins`; use `displayName` for labels, and a top-level `renames` map to migrate users — [host a marketplace](https://code.claude.com/docs/en/plugins/host-marketplace.md)

**Versioning and updates**
- Version resolution: manifest `version` first, then marketplace entry `version`, otherwise commit SHA (12 chars) for git-based sources. If `version` is set and you push without bumping, users do not get the change. Docs advise: bump on every release or omit it entirely; do not set it in both places — [host a marketplace](https://code.claude.com/docs/en/plugins/host-marketplace.md), [loading reference](https://code.claude.com/docs/en/plugins/loading.md)
- Installed copies are cached at `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`; old versions get an `.orphaned_at` marker and are deleted after 14 days — [loading reference](https://code.claude.com/docs/en/plugins/loading.md)
- Auto-update is on by default for Anthropic's official marketplaces, off for every other marketplace (turn on per marketplace via `/plugin` > Marketplaces > Enable auto-update, or `autoUpdate` in an `extraKnownMarketplaces` entry); runs after the first message with a random delay up to 10 minutes; the running session keeps old versions until `/reload-plugins`. `DISABLE_AUTOUPDATER` and similar turn it off unless `FORCE_AUTOUPDATE_PLUGINS=1` — [loading reference](https://code.claude.com/docs/en/plugins/loading.md)
- `claude plugin update name@marketplace` and `/plugin marketplace update name` are the manual routes; `ref`/`sha` on an entry or `#ref` on the add command hold users on a branch or tag; release channels are two marketplaces with different names — [host a marketplace](https://code.claude.com/docs/en/plugins/host-marketplace.md)
- Mid-session, hooks/MCP/LSP keep the previous version's path until `/reload-plugins`; monitors need a restart — [loading reference](https://code.claude.com/docs/en/plugins/loading.md)

**Private GitHub marketplaces**
- Claude Code has no git token of its own and `marketplace.json` has no credential field; it runs `git` on the user's machine non-interactively with existing credentials. For GitHub `owner/repo` it tries SSH first and falls back to HTTPS; HTTPS works through a credential helper (run `gh auth login` then `gh auth setup-git`). A bare `GITHUB_TOKEN` env var alone does not authenticate background auto-update, it must reach a credential helper — [host a marketplace](https://code.claude.com/docs/en/plugins/host-marketplace.md)
- `CLAUDE_CODE_PLUGIN_PREFER_HTTPS=1` skips the SSH probe; installs from `/plugin` inside a session and updates do not fall back to HTTPS automatically. If a background update cannot authenticate, Claude Code re-clones (and keeps the old checkout if that fails); `CLAUDE_CODE_PLUGIN_KEEP_MARKETPLACE_ON_FAILURE=1` skips the re-clone — [host a marketplace](https://code.claude.com/docs/en/plugins/host-marketplace.md)
- Users without git accounts can be served via `archive` sources (zip over HTTPS, pin `sha256`), but that is irrelevant to a single-user private repo — [host a marketplace](https://code.claude.com/docs/en/plugins/host-marketplace.md)
- For CI, give the runner a `GH_TOKEN` and run `gh auth setup-git`; the default workflow token cannot read another private repo — [org docs](https://code.claude.com/docs/en/plugins/org.md)

**Project-level enablement**
- Settings sources for `enabledPlugins`, low to high: `--add-dir`, user (`~/.claude/settings.json`), project (`.claude/settings.json`), local (`.claude/settings.local.json`), `--settings` flag, managed. Values merge key by key; the highest source mentioning a plugin id wins — [loading reference](https://code.claude.com/docs/en/plugins/loading.md)
- Per-repo pattern: put `extraKnownMarketplaces` (keyed by the marketplace's own `name`, `source: {source: github, repo: ...}`, optional `autoUpdate`) and `enabledPlugins` (`plugin@marketplace: true`) in the repo's `.claude/settings.json`. `extraKnownMarketplaces` applies only after the user accepts the workspace trust dialog and is silently ignored in untrusted folders and in `-p` runs of untrusted folders — [org docs](https://code.claude.com/docs/en/plugins/org.md)
- A plugin listed by relative path in the marketplace loads from the marketplace copy once those entries apply; a plugin with an external source (its own GitHub repo) is not fetched from project settings alone: teammates see "enabled in project settings but isn't installed" until they run `claude plugin install name@marketplace --scope project`. Only user settings, an untracked `settings.local.json`, `--settings` or managed settings trigger fetching external-source plugins — [org docs](https://code.claude.com/docs/en/plugins/org.md), [loading reference](https://code.claude.com/docs/en/plugins/loading.md)
- `claude plugin marketplace add owner/repo --scope project` writes the committed `.claude/settings.json` entry for you — [host a marketplace](https://code.claude.com/docs/en/plugins/host-marketplace.md)
- Plugins can also live in `.claude/skills/` as skills-directory plugins (a folder with `.claude-plugin/plugin.json`); they load from the primary working directory only, not parent directories, and only after folder trust; Claude Code does not scan a project `.claude/plugins/` folder — [loading reference](https://code.claude.com/docs/en/plugins/loading.md)
- Trust: project-scope plugins load only after the same trust check as project allow rules; trusting a parent folder or `-p` is not enough — [loading reference](https://code.claude.com/docs/en/plugins/loading.md)
- Name conflicts: plugin skills are namespaced so a personal skill and a same-named plugin skill both load; between non-plugin skills personal beats project — [skills docs](https://code.claude.com/docs/en/skills)
- Synced plugins: plugins turned on for the user's claude.ai account load as `name@synced` in terminal sessions (v2.1.273+), and Cowork does not load a plugin with a top-level `bin/` — [loading reference](https://code.claude.com/docs/en/plugins/loading.md)

### Inferences
- The reader's architecture (private GitHub repo as marketplace plus plugin, enabled per project in `.claude/settings.json`) is supported. Easiest robust shape: single repo with `.claude-plugin/marketplace.json` listing the plugin at a relative path (`./plugin` or `./`), so project settings alone are enough on teammates' machines once they trust the folder and have git credentials.
- Omit `version` while iterating alone (every push becomes an update, tracked by SHA) or bump it for releases; never both; enable auto-update on the private marketplace manually or via `autoUpdate` in the committed `extraKnownMarketplaces` entry, and ensure `gh auth setup-git` has been run on Windows so background updates do not fail quietly.
- Because a plugin cannot carry CLAUDE.md, workspace-level behaviour (language rules, "never use em-dash", log conventions) must live in the workspace template's CLAUDE.md/AGENTS.md or in a SessionStart hook that prints a short instruction block, as Superpowers' bootstrap does. A hook also lets the plugin inject a pointer to `workspace.yaml`.
- The 1,536-character description cap and the always-in-context description cost argue for `disable-model-invocation: true` on rarely used skills and tight descriptions.
- A Windows user should test hooks under both Git Bash and PowerShell, since Superpowers needed a dedicated `run-hook.cmd` and PowerShell variant and shipped several Windows fixes in 7.0.x.

### Gaps
- I did not fetch the plugin dependency version docs or the `marketplace-reference` source-type details beyond the quoted summaries.
- Behaviour of Cursor and Copilot plugin installs from a Claude-format marketplace was not verified beyond Superpowers' README commands.
- Whether Claude Code in the desktop app (the user's environment) behaves identically for project-scoped plugin trust was not tested.

## 3. How do people keep one source of truth for rules across agents?

### Takeaway
AGENTS.md is the de facto cross-tool standard (stewarded by the Agentic AI Foundation under the Linux Foundation) and since Claude Code v2.1.277 Claude reads it natively, but only when no CLAUDE.md exists above the working directory. The practical pattern for a Claude-primary user is a CLAUDE.md containing `@AGENTS.md` (import) rather than a symlink, particularly on Windows; generators such as rulesync and ruler are only worth it if you also need to sync commands, MCP and skills to many tools.

### Cited Findings
- agents.md lists support from Codex, Jules, Factory, Aider, goose, opencode, Zed, Warp, VS Code, Devin, Junie, Amp, Cursor, RooCode, Gemini CLI, Kilo Code, Copilot coding agent, Windsurf, Augment and others; stewarded by the Agentic AI Foundation under the Linux Foundation; closest file to the edited file wins; explicit chat prompts override. The page does not mention Claude Code — [agents.md](https://agents.md)
- Claude Code docs: "Claude Code can read AGENTS.md as your project instructions" without CLAUDE.md, an import or a setting, requiring v2.1.277 or later. By default it reads AGENTS.md only when there is no CLAUDE.md, .claude/CLAUDE.md or CLAUDE.local.md in the working directory or above; if both exist, only CLAUDE.md is read. `~/.claude/CLAUDE.md`, org-managed CLAUDE.md and `.claude/rules/` do not count for that check and still load — [memory docs](https://code.claude.com/docs/en/memory)
- A `CLAUDE.local.md` counts as a CLAUDE.md, so adding one to a repo that relies on AGENTS.md stops Claude reading AGENTS.md unless the Project instructions setting is `claude-md-and-agents-md` (set in `/config` or via `pluginConfigs` `cc-plugin-agents-md@builtin` in user/managed settings; ignored in project settings) — [memory docs](https://code.claude.com/docs/en/memory)
- Some sessions cannot read AGENTS.md directly (built-in plugin disabled, first session after upgrade, and before v2.1.281 Bedrock or telemetry-disabled sessions); the documented fallback is a CLAUDE.md containing `@AGENTS.md` plus Claude-specific notes below — [memory docs](https://code.claude.com/docs/en/memory)
- Symlink caveats from the docs: Edit/Write tools refuse to write through a symlink; on Windows creating symlinks needs Administrator or Developer Mode and Git checks a committed symlink out as a one-line text file unless `core.symlinks` is enabled, so "use the `@AGENTS.md` import instead" if anyone on Windows works in the repo — [memory docs](https://code.claude.com/docs/en/memory)
- `AGENTS.md` read via the setting does not fire `InstructionsLoaded` hooks, while an imported or symlinked one does — [memory docs](https://code.claude.com/docs/en/memory)
- `.claude/rules/` supports symlinks for shared rule sets and path-scoped rules via `paths` frontmatter; symlink targets outside the working directory are treated like external imports requiring approval; network (UNC) paths are not followed — [memory docs](https://code.claude.com/docs/en/memory)
- Cursor: reads AGENTS.md in the root and subdirectories (nested files combine, more specific wins) as an alternative to `.cursor/rules/*.mdc` (which has four application types); the page does not mention CLAUDE.md or skills — [Cursor rules docs](https://cursor.com/docs/context/rules)
- GitHub Copilot: `.github/copilot-instructions.md` (repo-wide), `.github/instructions/*.instructions.md` with `applyTo` (cloud agent and code review only on github.com), plus AGENTS.md (nearest wins) and a single root CLAUDE.md or GEMINI.md; code review reads instructions and skills from the PR head branch — [Copilot docs](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions)
- Codex discovers skills from `$CWD/.agents/skills` up to the repo root, `$HOME/.agents/skills`, `/etc/codex/skills`, plus bundled system skills; a skill needs `name` and `description`; same-named skills are not merged; plugins distribute skills through a shared universal plugin directory — [Codex skills docs](https://learn.chatgpt.com/docs/build-skills)
- OpenCode searches `~/.config/opencode/skills`, `~/.claude/skills`, `~/.agents/skills` globally and `.opencode/skills`, `.claude/skills`, `.agents/skills` per project (walking up to the project root); skills sources can also be added in `opencode.json` — [OpenCode skills docs](https://opencode.ai/docs/skills/)
- Skills follow the open Agent Skills standard (agentskills.io); outside Claude Code (claude.ai upload, Skills API) only `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools` frontmatter fields are allowed and extra fields cause a hard error — [skills docs](https://code.claude.com/docs/en/skills)
- Rulesync (1.6k stars, active 2026-11-09) is an npm/Homebrew CLI that generates configuration for many tools from unified rule files and covers rules, commands, MCP, ignore files, subagents and skills — [rulesync](https://github.com/dyoshikawa/rulesync); Ruler (3k stars, active 2026-11-04) is "apply the same rules to all coding agents" — [ruler](https://github.com/intellectronica/ruler)
- A secondary guide (not verified against the npm registry) warns that rulesync published majors 18 to 21 within three days in September 2026 so an unpinned `npx rulesync` can change CI output; pin the version — [search summary of developertoolkit.ai](https://developertoolkit.ai/en/ecosystem/frameworks/rules-sync/)
- Community guidance is consistent that AGENTS.md is the canonical file and CLAUDE.md should import or link to it; opinions differ on whether the symlink drawbacks matter (secondary sources) — [search results incl. travis.media and dev.to](https://travis.media/blog/claude-md-import-agents-md)
- Spec Kit takes the opposite approach: an agent-neutral `none` integration with per-developer switching rather than a shared generated file — [Spec Kit integrations doc](https://github.com/github/spec-kit/blob/main/docs/integrations/index.md)
- wshobson/agents uses CI-regenerated per-tool artifacts from one Claude-format source; Superpowers keeps one set of skills plus per-host manifests/hooks directories — [wshobson/agents](https://github.com/wshobson/agents), [Superpowers](https://github.com/obra/superpowers)

### Inferences
- For one user primarily on Claude Code: keep the real content in AGENTS.md at the workspace root, and have CLAUDE.md contain `@AGENTS.md` plus Claude-only notes; this works on Windows, keeps Edit/Write usable, and still serves Codex/Cursor/Copilot/OpenCode developers sharing the repo. A symlink is risky on Windows.
- Because Codex and OpenCode both scan `.agents/skills` and OpenCode also scans `.claude/skills`, a skills source of truth in `.claude/skills` plus a directory symlink or copy into `.agents/skills` would reach three tools without a generator; the cost is the symlink problem again on Windows. Not verified for Cursor and Copilot.
- Generators (rulesync, ruler) add a tool dependency and version churn; justify them only if the kit must also sync commands/MCP to non-Claude tools. For a documentation-and-design workflow with occasional developers, the AGENTS.md import is likely enough.
- Gotcha for the user's own workspace: it already has a CLAUDE.md, so Claude will not read an AGENTS.md unless CLAUDE.md imports it or the setting is changed.

### Gaps
- I did not verify exact Cursor and Copilot behaviour for skills directories or whether they read `.agents/skills`.
- I did not read rulesync's or ruler's own docs for supported targets or Windows behaviour beyond README summaries.
- agents.md was fetched with a summarising tool; membership of the foundation and the tool list should be rechecked on the live page if quoted.

## 4. Per-project settings, scaffolding, and combining kits without conflicts

### Takeaway
Spec-style kits use an init CLI that writes a project directory (`.specify/`, `openspec/`, `_bmad/`, agent-os folder) plus per-tool command files and a single YAML config; plugin-style kits (Superpowers, CE) use either nothing (Superpowers) or a small repo config file created by a setup skill (CE `.compound-engineering/config.yaml`). Combining kits is mostly safe at the plugin level thanks to namespacing, but the risks are bootstrap-prompt competition, same-name plugins, duplicated skills and token overhead.

### Cited Findings
- OpenSpec: `openspec init` creates `openspec/` and tool files; per-project `openspec/config.yaml` holds schema, `context`, `rules` per artifact and `operations` guidance; `openspec update` refreshes generated files — [customization doc](https://github.com/Fission-AI/OpenSpec/blob/main/docs/customization.md)
- Spec Kit: `specify init --integration <key>` creates the project scaffold (a `.specify/` folder with a `memory/constitution.md`), templates and agent commands; per-project customisation is via presets or project-local overrides, not by editing generated files — [Spec Kit repo](https://github.com/github/spec-kit), [integrations doc](https://github.com/github/spec-kit/blob/main/docs/integrations/index.md)
- CE: `/ce-setup` creates `.compound-engineering/config.yaml` when missing and gitignores an existing local override; config template carries a version line and setup rebuilds an older `config.yaml` on the new template while keeping settings; ordinary keys read local then repo file, first active value wins; a present list or map replaces the key wholesale (but `packs` lists concatenate); `docs_root` only from the tracked file and fails closed — [configuration guide](https://github.com/EveryInc/compound-engineering-plugin/blob/main/docs/guides/configuration.md)
- Agent OS: base install with profiles and `inherits_from`, scripts to install into projects and sync project standards back to the profile — [config.yml](https://github.com/buildermethods/agent-os/blob/main/config.yml), [CHANGELOG](https://github.com/buildermethods/agent-os/blob/main/CHANGELOG.md)
- BMAD v7: `bmad setup` skill installs and refreshes; BMAD issues show per-project render state under `_bmad/` that was not git-ignored and blocked its own build on a dirty tree (#3149), duplicated review layers between two of its skills (#2760), and recursive agent delegation token waste (#2987) — [BMAD issues](https://github.com/bmad-code-org/BMAD-METHOD/issues)
- gstack team mode: commits a `required` hook into the repo's `.claude/` and CLAUDE.md so teammates auto-install it; teammates need Node on PATH; `required` can be swapped for `optional` — [gstack README](https://github.com/garrytan/gstack)
- Superpowers has no per-project config; project behaviour changes through your own CLAUDE.md or by invoking skills directly. Its bootstrap re-fires on `startup|clear|compact`, and skills re-attached after compaction are cut at 20,000 characters (docs now say first 5,000 tokens per skill, 25,000 tokens combined, newest-invoked first) — [release notes 7.0.1](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md), [skills docs](https://code.claude.com/docs/en/skills)
- Superpowers' SDD helper scripts now act on the repository of the current directory and require a git repo with at least one commit; they write workspace files under `.superpowers/sdd/` — [release notes 7.0.2](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)
- A Superpowers user reported that Superpowers files and instructions appeared in two projects without their consent and that agents prioritised Superpowers' plans over their instructions (open, 2026-11-07, one user's account; cause not established) — [issue 2677](https://github.com/obra/superpowers/issues/2677)
- Superpowers issue 2377 (open, 2026-09-24) argues the bootstrap wraps `using-superpowers` in `<EXTREMELY_IMPORTANT>` with "If you think there is even a 1% chance a skill might apply... you ABSOLUTELY MUST invoke", which current models follow literally, over-triggering skills on trivial requests and escalating to spec and plan; re-injected after each compaction — [issue 2377](https://github.com/obra/superpowers/issues/2377)
- Superpowers 7.0.2 answered part of that by making brainstorming ask fewer questions and "stops asking about process" — [release notes](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)
- Claude Code namespaces plugin skills so personal/project skills and plugin skills with the same short name both load, `/plugin-name:skill-name` — [skills docs](https://code.claude.com/docs/en/skills)
- `claude plugin validate` and the `/plugin` Errors tab show duplicated-name conflicts; two plugins with the same manifest name leave one set of hooks inactive — [loading reference](https://code.claude.com/docs/en/plugins/loading.md)
- Secondary comparisons recommend pairings such as BMAD for architecture with Superpowers for TDD, or OpenSpec for incremental change with Superpowers as quality gates; they describe the kits as different layers (SEO-grade sources) — [web search summary](https://developertoolkit.ai/en/ecosystem/frameworks/spec-driven-frameworks/)
- CE disclosed that its docs artifacts default to `docs/plans` and `docs/solutions` and offers `docs_root` to relocate them; Superpowers writes designs to `docs/plans/YYYY-MM-DD-<topic>-design.md` per an open efficiency issue quoting its brainstorming skill — [CE config guide](https://github.com/EveryInc/compound-engineering-plugin/blob/main/docs/guides/configuration.md), [Superpowers issue 512](https://github.com/obra/superpowers/issues/512)

### Inferences
- Two methodology plugins (Superpowers plus CE, or plus BMAD) both want to own the plan/brainstorm entrypoint; running both means competing session-start instructions and duplicated plan folders (`docs/plans` is a default for both), which is a likely conflict I did not see tested anywhere. Superpowers plus a personal skills plugin with distinct skill names is low risk because of namespacing.
- The reader's own plugin should define skill names that do not overlap with Superpowers (brainstorming, writing-plans, etc.) and give each a "when to use" boundary, otherwise the model chooses between near-duplicate descriptions; keep a workspace-specific bootstrap short and not in all-caps pressure language.
- For a documentation and design workspace, a single `workspace.yaml` read by the plugin's skills and hooks mirrors the OpenSpec `config.yaml` and CE `config.yaml` patterns (context plus per-artifact rules, committed base file, optional local override that wins per key, versioned template so a setup skill can migrate it, a fail-closed path setting). Those three details came from CE and OpenSpec and are the most reusable.
- A per-project init is best a skill or script that is idempotent, preserves user edits, and records a template version, as CE `/ce-setup` and Agent OS sync scripts do; an upgrade breakage cluster in several kits (CE stale marketplace snapshot, Spec Kit CLI versus project file upgrade split, BMAD v6 versus v7) shows the cost of generated files drifting from the kit.

### Gaps
- No source tested running Superpowers together with CE or BMAD; conflict claims are inferred.
- I did not verify how Superpowers' `.superpowers/` workspace folder interacts with non-code repos (documentation workspaces without git commits); the release notes say it requires `git init` and a first commit.
- Spec Kit `.specify/` directory contents were only partially listed (memory/constitution.md seen via the API).

## 5. What are the common failure modes reported by users?

### Takeaway
Reported problems cluster into: token and cost overhead (always-loaded descriptions, subagent loops, multi-agent review), too much ceremony for small tasks, skills that over-trigger or do not trigger, stale or conflicting instructions after compaction, and upgrade breakage from generated files or cached marketplaces. The best independent data point (Surge HQ, 100 tasks) shows large cost differences between kits with small quality differences.

### Cited Findings

**Token cost and slowness**
- Surge HQ benchmark: vanilla at xhigh effort +11.3 points over medium at 3.5x cost; Superpowers +2.4 at about 1.1x; /goal plus /code-review +3.3 at 1.8x; Compound Engineering 8x cost without statistically clear improvement; the authors caution the result is one model on one task distribution — [Surge HQ](https://surgehq.ai/blog/benchmarking-coding-agent-harnesses)
- CE maintainer response on the 8x issue: every plan gets 3-5 doc reviewers "no matter how small the change is" and `lfg` simplifies above a threshold; "sometimes it's too much and something that we continually look at tuning"; the reporter suggested a routing step — [CE issue 1999](https://github.com/EveryInc/compound-engineering-plugin/issues/1999)
- CE at one point used about 36k tokens of context just by being enabled (30 agents about 8.6k, about 40 skills about 11k, plus Playwright and Context7 MCP 16.4k); issue closed — [CE issue 63](https://github.com/EveryInc/compound-engineering-plugin/issues/63) (also "High idle usage ~12k tokens" [issue 139](https://github.com/EveryInc/compound-engineering-plugin/issues/139))
- Superpowers: "slowness in responses since using the skill" (27 comments, open since 2026-03) — [issue 743](https://github.com/obra/superpowers/issues/743); a 15-task port of a 2,000-line R script hit 5 session limits with coordinator context growing to 830k tokens under subagent-driven development on Claude Code (open, 2026-10-23) — [issue 2612](https://github.com/obra/superpowers/issues/2612); Codex SDD run consuming a full 5-hour budget on a simple plan — [issue 1152](https://github.com/obra/superpowers/issues/1152); reviewer verbosity — [issue 1930](https://github.com/obra/superpowers/issues/1930)
- Secondary: A/B tests of 12 sessions reported roughly 9-14% lower token use with Superpowers but small samples and non-uniform results; reports of "incredibly verbose about simple things" are quoted second-hand — [MindStudio and Towards AI via search summary](https://www.mindstudio.ai/blog/5-claude-code-skills-cut-token-costs-70-percent-benchmarked) (low confidence)
- Plugin enabled-by-default cost: skill descriptions are always in context unless `disable-model-invocation: true` — [skills docs](https://code.claude.com/docs/en/skills)

**Too much ceremony**
- Superpowers issue 2530 "v7's brainstorm questions are rather annoying" is the most-commented open issue (34 comments); maintainers retuned brainstorming in 7.0.1 and 7.0.2 — [issue 2530](https://github.com/obra/superpowers/issues/2530), [release notes](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)
- Fowler/Böckeler on Spec Kit: "overkill for the size of the problem", many repetitive markdown files, false sense of control — [martinfowler.com](https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- Agent OS's own v3 rationale: plan mode and frontier models make heavy scaffolding unnecessary — [CHANGELOG](https://github.com/buildermethods/agent-os/blob/main/CHANGELOG.md)

**Skills that do not trigger or over-trigger**
- Eval by a user (open 2026-09-25): with Superpowers 6.4.1 on Opus 5.5, a plain "add a slugify function" request called no `Skill` in 3 runs and TDD was not invoked even with the bootstrap present — [issue 2386](https://github.com/obra/superpowers/issues/2386)
- Opposite problem: the pressure-language bootstrap over-triggers on trivial requests and escalates to spec and plan — [issue 2377](https://github.com/obra/superpowers/issues/2377)
- Codex Desktop: brainstorming approval gates skipped after skill read (6.4.1) — [issue 2372](https://github.com/obra/superpowers/issues/2372)
- Hosts without session-start hooks rely on skill descriptions to load the bootstrap (Antigravity), and Hermes loses it after compaction: "start a fresh session if skills stop triggering" — [README](https://github.com/obra/superpowers)
- Superpowers ships a `diagnosing-superpowers` skill that reads the session transcript to explain misfires — [README](https://github.com/obra/superpowers)

**Conflicting or lost instructions**
- Skills re-attached after compaction are truncated; one reported session lost SDD's five-round limit and ran 18 fix rounds. Superpowers moved detail into `references/` and added a test that fails if a SKILL.md reaches 20,000 bytes — [release notes 7.0.1](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)
- Claude Code docs: instructions are context, not enforced configuration; to block an action use a PreToolUse hook — [memory docs](https://code.claude.com/docs/en/memory)
- OpenSpec `MODIFIED` requirement headers that rename a scenario are read as a dropped scenario and block archive (issue 1697); validation catches some inconsistencies only at archive — [OpenSpec issues](https://github.com/Fission-AI/OpenSpec/issues)
- Spec Kit: grep-based alignment and renumbering pain are the most-commented feature requests (stable IDs, structured IDs, deterministic IDs) — [Spec Kit issues](https://github.com/github/spec-kit/issues)
- One open user report (2026-11-07), "Superpowers Appeared Without My Consent...", alleges agents prioritised Superpowers' plans over explicit instructions; the reporter says causation is not established, so weight lightly — [issue 2677](https://github.com/obra/superpowers/issues/2677)

**Upgrade breakage and install fragility**
- CE: `/plugin update` alone leaves users on the old version after the layout change; legacy Bun installs left a stale tool map in the global Codex AGENTS.md and could shadow native plugin skills; a SKILL.md `name` field was ignored so `/ce:brainstorm` required `/compound-engineering:ce-brainstorm` (issue 314) — [upgrading doc](https://github.com/EveryInc/compound-engineering-plugin/blob/main/docs/install/upgrading.md), [issues](https://github.com/EveryInc/compound-engineering-plugin/issues)
- Superpowers: Windows hook problems (broken PATH, WSL bash launchers, PowerShell ParserError, exit codes not passed) fixed across 7.0.0 and 7.0.2; six child-process launches per startup cost tens of milliseconds each on Git Bash; helpers wrote into the plugin cache when run outside a repo — [release notes](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)
- BMAD: v6 to v7 transition with "expect breaking changes", script files shipped without helper modules (#3008), directories created mode 0700 (#3134), YAML frontmatter parse failures so `npx skills add` skips a skill (#3130) — [BMAD issues](https://github.com/bmad-code-org/BMAD-METHOD/issues), [README](https://github.com/bmad-code-org/BMAD-METHOD)
- Spec Kit: generated agent files should not be hand-edited; upgrade is two commands and `uv tool install` repeated does not upgrade; on Windows `specify self upgrade` for uv installs prints a command to run after exit — [upgrade guide](https://github.com/github/spec-kit/blob/main/docs/upgrade.md)
- Agent OS: silent install failures under `set -e` and macOS `tac` portability were still "Unreleased" at the last release — [CHANGELOG](https://github.com/buildermethods/agent-os/blob/main/CHANGELOG.md)
- gstack: host table shows non-Claude agents get advisory-only safety skills and only Claude Code is "full" tier — an example of portability caveats — [gstack README](https://github.com/garrytan/gstack)
- Cross-host: Superpowers states users must install separately for each harness and several maintainers list "same skills across harnesses" as a hard requirement for contributions — [README](https://github.com/obra/superpowers)
- Plugin marketplace layer: unnecessary version pinning causes silent non-updates ("If you set version 1.0.0 and push new commits... users don't receive them"); private HTTPS marketplaces fail quietly in background update without a stored credential — [host a marketplace](https://code.claude.com/docs/en/plugins/host-marketplace.md)
- Gaining popularity but low maintenance: gsd-build/get-shit-done, 64k stars, no push since 2026-05-31; travisvn/awesome-claude-skills no push since April — [get-shit-done](https://github.com/gsd-build/get-shit-done), [awesome-claude-skills](https://github.com/travisvn/awesome-claude-skills)

### Inferences
- The strongest evidence-based adopt/avoid signal: Superpowers has a measured ~10% cost overhead and modest quality gain on engineering tasks, CE is expensive for small tasks; neither benchmark covers documentation or design work, so benefits for the reader's workflow are unmeasured. Treat Superpowers' TDD/worktree/SDD skills as largely irrelevant to documentation and design; value is in brainstorming and verification-before-completion, which can be invoked by name.
- Over-triggering and under-triggering both stem from instruction text in a hook, so the reader should keep their own bootstrap minimal, avoid pressure language, and check with `/context` and the `diagnosing-superpowers` pattern. A plugin's skills cannot be edited in place, so the realistic levers for Superpowers are disabling the plugin per project (`"superpowers@...": false` in `.claude/settings.local.json`, which beats the project file) or using a fork; this is inferred from the settings precedence documented in the loading reference.
- Upgrade breakage is mostly where kits write generated files into projects; a kit that stores everything in the plugin and one small versioned config file avoids most of it.
- Heavy per-project generated artifacts are where critics concentrate (Fowler, BMAD issues); the lightest kits (Superpowers, OpenSpec core profile, Agent OS v3) draw fewer structural complaints.

### Gaps
- No peer-reviewed or large-sample study of kit effectiveness; Surge is a single vendor benchmark. Its text did not reproduce chart values; only the stated deltas are cited. The page did not explicitly name which plugin used 37 skills and 17 agents beyond the CE issue discussion.
- Reddit and Hacker News threads were not retrieved; sentiment from them is absent.
- No data on skills that fail on Windows beyond Superpowers' fixes.
