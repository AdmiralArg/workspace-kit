# Documentation-as-memory workspaces: patterns, maintenance, agent-usable docs, drift control, shared layers (state as of 10 November 2026)

## 1. Karpathy's "LLM wiki" pattern: parts, operations, index/log, adoption reports

### Takeaway
Karpathy's gist (4 April 2026) defines three layers (immutable raw sources, an LLM-owned wiki of markdown, a schema file such as CLAUDE.md/AGENTS.md), three operations (ingest, query, lint) and two special files (content-oriented index.md, append-only log.md with greppable `## [date] type | title` headers). Adopters report it works well at about 100 sources or a few hundred pages, and breaks on drift between changelog and reference text, silent contradictions, orphans, a single index that outgrows context, and concurrent writes. The fixes people converge on are deterministic lint scripts, per-layer single authorship, verified citations to immutable raw sources, and human review gates.

### Cited Findings
**The gist itself (primary source)**
- Gist "LLM Wiki" is an "idea file" meant to be pasted into your own agent (Codex, Claude Code, OpenCode/Pi); it deliberately leaves directory structure, page formats and tooling to the agent and user. — [Karpathy gist, raw text](https://gist.githubusercontent.com/karpathy/442a6bf555914893e9891c11519de94f/raw)
- Created 4 April 2026 16:25; page shows 5,000+ stars and 5,000+ forks; comments still being added as late as 27 October 2026 (gh API reported ~30 comments on first page of comments, the page has more). — [gist page](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f); comment dates via GitHub API on the same gist
- Core claim: RAG rediscovers knowledge on every question; instead the LLM "incrementally builds and maintains a persistent wiki" so cross-references and contradiction flags already exist. Analogy: Obsidian is the IDE, the LLM is the programmer, the wiki is the codebase. Humans curate sources and ask questions; the LLM does bookkeeping. — [gist](https://gist.githubusercontent.com/karpathy/442a6bf555914893e9891c11519de94f/raw)
- Three layers: (1) Raw sources, immutable, "your source of truth", LLM reads but never modifies; (2) The wiki, LLM-generated markdown (summaries, entity pages, concept pages, comparisons, overview, synthesis), LLM owns it entirely; (3) The schema, a document like CLAUDE.md or AGENTS.md describing structure, conventions and workflows, "the key configuration file", co-evolved by human and LLM. — [gist](https://gist.githubusercontent.com/karpathy/442a6bf555914893e9891c11519de94f/raw)
- Ingest: drop a source, LLM reads it, discusses takeaways, writes a summary page, updates the index, updates relevant entity/concept pages, appends to the log. One source may touch 10-15 pages. Karpathy prefers one source at a time with human involvement; batch ingest is possible with less supervision. — [gist](https://gist.githubusercontent.com/karpathy/442a6bf555914893e9891c11519de94f/raw)
- Query: LLM searches wiki, reads pages, answers with citations; "good answers can be filed back into the wiki as new pages" so explorations compound. Output forms include markdown page, table, Marp slides, matplotlib chart, canvas. — [gist](https://gist.githubusercontent.com/karpathy/442a6bf555914893e9891c11519de94f/raw)
- Lint: periodic health check for contradictions, stale claims superseded by newer sources, orphan pages, concepts mentioned without their own page, missing cross-references, data gaps fillable by web search; LLM also suggests new questions and sources. — [gist](https://gist.githubusercontent.com/karpathy/442a6bf555914893e9891c11519de94f/raw)
- index.md is content-oriented: every page with link, one-line summary, optional metadata (date, source count), organised by category, updated on every ingest; LLM reads it first at query time. Works "surprisingly well" at about 100 sources / hundreds of pages without embedding RAG. — [gist](https://gist.githubusercontent.com/karpathy/442a6bf555914893e9891c11519de94f/raw)
- log.md is chronological and append-only (ingests, queries, lint passes). Tip: a consistent prefix like `## [2026-04-02] ingest | Article Title` makes it parseable, e.g. `grep "^## \[" log.md | tail -5`. — [gist](https://gist.githubusercontent.com/karpathy/442a6bf555914893e9891c11519de94f/raw)
- Optional tooling: qmd (local markdown search, hybrid BM25/vector with LLM re-ranking, CLI plus MCP) once the index is not enough; Obsidian Web Clipper; download images locally; Dataview over YAML frontmatter; "the wiki is just a git repo of markdown files" for history and collaboration. — [gist](https://gist.githubusercontent.com/karpathy/442a6bf555914893e9891c11519de94f/raw)
- Business/team variant is mentioned: internal wiki fed by Slack threads, meetings, documents, "possibly with humans in the loop reviewing updates". — [gist](https://gist.githubusercontent.com/karpathy/442a6bf555914893e9891c11519de94f/raw)
- Original social post dated 2 April 2026 in one archived copy (others say 3 April); engagement numbers (40k likes, 10.7M views) come from a third-party page and are unverified. — [VentureBeat](https://venturebeat.com/data/karpathy-shares-llm-knowledge-base-architecture-that-bypasses-rag-with-an); search summary of archived copy

**Concrete implementation details worth copying**
- Astro-Han skill: `raw/<topic>/YYYY-MM-DD-slug.md` with metadata header (source URL, collected date, published date); `wiki/<topic>/<article>.md`, one topic level only; `wiki/index.md` one row per article with link, summary and Updated date; `wiki/log.md` entries like `## [YYYY-MM-DD] ingest | title` followed by Disposition/Raw/Updated lines, and `## [YYYY-MM-DD] lint | N issues found, M auto-fixed`. — [SKILL.md](https://github.com/Astro-Han/karpathy-llm-wiki/blob/main/SKILL.md)
- Same skill adds a triage step before compile (dispositions New / Update / Disputed / No material; "No material" means keep raw, log, stop, do not force an article from a thin source), and cascade updates (search the whole wiki for the source's entities, update every non-archive article affected; archive pages are point-in-time and never cascaded). — [SKILL.md](https://github.com/Astro-Han/karpathy-llm-wiki/blob/main/SKILL.md)
- Same skill's "Grounding Invariant": every number, date and quote in wiki/ must exist verbatim in the raw file linked in that article's Raw field; compile establishes it (locate before you write), lint verifies it with `scripts/check_evidence.py` which greps high-signal literals (large numbers, decimals, ISO dates, longer quotes) in the linked raws. Superseded or contradicted claims are kept and marked with Status blocks (Outdated with date, or Disputed), "never silently rewrite history". — [SKILL.md](https://github.com/Astro-Han/karpathy-llm-wiki/blob/main/SKILL.md)
- Same skill splits lint into safe auto-fixes (index consistency, internal links, raw references, See Also), mechanical reports (source fidelity, evidence errors, unreferenced raw files) and judgment reports (contradictions, outdated claims without status block, orphans, missing cross-references); it never auto-fixes facts. — [SKILL.md](https://github.com/Astro-Han/karpathy-llm-wiki/blob/main/SKILL.md)
- claude-obsidian schema (WIKI.md): `inbox/` (visible intake, never auto-deleted), `.raw/` (immutable, content-addressed by SHA-256 with manifest), `wiki/` with index.md, log.md (newest first), hot.md (bounded recent context, "not a transcript"), overview.md, sources/, entities/, concepts/, questions/, and `meta/ledgers/source-ledger.json` and `claim-ledger.json`. Required frontmatter: type, title, status, created, updated, tags (YYYY-MM-DD dates). — [WIKI.md](https://github.com/AgriciDaniel/claude-obsidian/blob/main/WIKI.md)
- claude-obsidian lint is a deterministic, read-only script (dead/ambiguous links, orphans, frontmatter gaps, empty sections, stale index entries, claim-ledger violations); it explicitly does not claim semantic contradiction analysis. Repair is a separate operation: record SHA-256 of targets, build a repair bundle, show exact changed paths, apply only after review, re-run lint. — [wiki-lint SKILL.md](https://github.com/AgriciDaniel/claude-obsidian/blob/main/skills/wiki-lint/SKILL.md)

**What adopters report works**
- Aaron Fulkerson (12 April 2026), production vault driven by 14 MCP servers and 26 skills: adding INDEX.md cut orientation time and tokens; LOG.md tracked staleness; YAML frontmatter tags each file as human-written, LLM-generated, or LLM-generated and human-reviewed so the model can gauge trust; first lint pass found 23 orphaned files and 11 broken cross-references. Instructions alone were unreliable, especially after context compaction, so enforcement moved to hooks (email send gate, post-compact state re-injection, post-commit observation capture). He only noticed the missing lint/index/log/provenance by comparing against Karpathy's gist. — [Fulkerson](https://aaronfulkerson.com/2026/04/12/karpathys-pattern-for-an-llm-wiki-in-production/)
- Exbrain 2.0 (chaenmasahiro0425, 66 stars, pushed 2026-07-05), from three months of running v1: "Raw logs pile up on their own, but compiled knowledge rots on its own." Fix: 4 layers raw (append-only daily/clips) -> wiki (entities, clients, decisions, research with source link on every claim and an expiry date) -> digest -> identity (humans only), nightly compile by a cheap model, weekly shell-only lint (broken links, duplicates, staleness, expired research), INDEX.md as front door with a freshness dashboard. "Separation of ownership": each layer has exactly one author so sync conflicts cannot occur. — [Exbrain README](https://github.com/chaenmasahiro0425/exbrain)

**What adopters report breaks**
- Michael Tuszynski (13 Aug 2026), six months in, several hundred pages over four domains: (1) changelog/reference drift, the agent appended dated entries but left reference sections describing retired systems as current; (2) silent contradictions, two entity pages for one institution caused double counting; (3) orphans and dead links accumulate faster than occasional lint catches, weekly lint recovered most. Diagnosis: "the wiki has no immune system against its own past." Fixes: Python drift linter flagging retired terms in live docs (runs pre-commit and cron; after a site migration it caught nine stale files including the top-level README), per-domain sub-schemas, a vector index as recall layer with the wiki still canonical, and a rule that a migration is only done when reference sections match new reality. Stated limits: no write locking (use a lockfile for concurrent agents); retrieval breaks past about 100k tokens of hot content; Claude-written conventions are hard for humans without the schema to read. Recommended start: one folder, one schema, five sources, one domain for two weeks; add drift check, weekly lint and the migration rule at 30-40 pages; add vector search only when the wiki no longer fits context. — [The Cloud Codex](https://www.mpt.solutions/karpathys-llm-wiki-works-heres-what-broke-when-i-ran-it-at-real-scale/)
- Comments and extensions on the v2 gist: index.md works to roughly 100-200 pages (one commenter says 200-500 documents); time-decay of confidence can hide superseded decisions that still explain current choices, prefer explicit supersession with git as audit trail; numeric confidence scores are "false precision"; small local models writing via hooks invent dependencies and silently corrupt the wiki, so use a human write gate; a podcast-wiki author keeps a "Disagreements & open questions" section because supersession fails when sources merely disagree; a relative permission rule `Edit(wiki/**)` stopped matching after the agent ran `cd wiki`, breaking unattended runs, so use absolute paths. — [LLM Wiki v2 gist](https://gist.github.com/rohitg00/2067ab416f7bbe447c1977edaaa681e2)
- Secondary summaries repeat: hallucinated links persist once written; at team scale thousands of documents make manual drift audits impossible; the term "LLM wiki" is used loosely for several different ideas. These are blog-level claims, not measured. — [WebSearch summary of multiple posts](https://www.mpt.solutions/tag/knowledge-management/)

### Inferences
- The reader's workspace already matches most of the gist's operations: `log.md` with machine-readable type prefix (identical to Karpathy's tip), inbox plus ingest, lint skill, per-project README/glossary/decisions. The missing pieces relative to the better implementations are (a) a generated, categorised index with one-line summaries and dates, (b) a deterministic lint script (path verification, stale terms, orphan check) distinct from the LLM judgment lint, (c) a frontmatter field for provenance/review status, (d) status blocks (Outdated/Disputed) instead of silent rewriting.
- Karpathy's "raw immutable" principle maps to the reader's Inbox plus source files: after ingest, raw files should become read-only references that wiki pages cite, so the existing citation rule (verifiable paths) is the equivalent of the Astro-Han grounding invariant. Extending the lint from "path exists" to "number/date/quote appears in cited file" is a small, high-value step.
- The most common failure (changelog updated, reference text not) is exactly what a project folder with README plus decisions plus log would suffer. A "retired terms" list checked by script is cheap and has a documented track record.
- Karpathy's pattern assumes a single curator. The reader is explicitly building a layer for others; the pattern gives little help there (see section 5).

### Gaps
- No exact star count for the Karpathy gist (page shows "5,000+" only); total comment count not retrieved.
- Could not verify Karpathy's own claim of wiki size (secondary sources say about 100 articles and 400,000 words); not included as fact.
- No independent, quantified study of LLM-wiki failure at scale; all reports are single practitioner anecdotes or vendor posts. No Karpathy follow-up post about lint was found.
- Last-commit dates for nashsu/llm_wiki etc. are "last push" from the GitHub API, not necessarily last meaningful commit.

## 2. Other patterns: Cline Memory Bank, ADRs, session logs, docs-for-agents folders, Obsidian/second-brain, PARA, spec/PRD folders

### Takeaway
Every pattern is a variation on "markdown files an agent reads at session start and updates at session end"; they differ in what is always loaded (Memory Bank: all files every task) versus loaded on demand (skills, path-scoped rules, indexes). Reported weaknesses repeat: manual upkeep, stale "active" files, token cost of always-loading, and authority problems when old decisions are treated as binding.

### Cited Findings
**Cline Memory Bank (2025)**
- Layout: `memory-bank/` with projectbrief.md (foundation), productContext.md (why), activeContext.md (current focus, changes most often), systemPatterns.md, techContext.md, progress.md (status/known issues); extra files allowed. Cline is required to read all files at the start of every task; commands "initialize memory bank", "follow your custom instructions", "update memory bank". Docs advise starting with a basic brief, updating activeContext after each session, and note it is not a replacement for a README. — [Cline docs](https://docs.cline.bot/features/memory-bank.md)
- Memory Bank is a community-created custom instruction set, not a built-in feature; the introductory blog (6 Feb 2025, Cline product marketing) is promotional, gives no benchmarks, and acknowledges dependence on model compliance and the maintenance burden of multiple consistent files. — [Cline blog](https://cline.bot/blog/memory-bank-how-to-make-cline-an-ai-agent-that-never-forgets)
- Critiques found are vendor blogs: the file most likely to be stale (activeContext) is the one leaned on hardest; oversized banks waste tokens loading stale information; always-injected versus on-demand figures are single-vendor self-reports. No independent critique or benchmark found. — [WebSearch results incl. fast.io, memorylake.ai](https://fast.io/resources/cline-memory-bank-guide/)

**Anthropic's own memory mechanisms and context-engineering guidance**
- Anthropic (29 Sept 2025): agents benefit from structured note-taking (e.g. a NOTES.md the agent maintains and re-reads after context resets), just-in-time retrieval via lightweight references (paths, queries, links), and progressive disclosure where file size, naming and timestamps act as relevance signals. Claude Code is hybrid: CLAUDE.md loaded up front, glob/grep for the rest. — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Claude Code memory docs: CLAUDE.md is instructions you write; auto memory is notes Claude writes, only the first 200 lines or 25KB load each session. Target under 200 lines per CLAUDE.md, move partial-scope material to skills or path-scoped `.claude/rules/` (paths frontmatter); @imports do not reduce context cost; contradictory instructions may be resolved arbitrarily so review periodically; `/doctor prompt-audit` checks instruction files; block-level HTML comments in CLAUDE.md are stripped before injection (maintainer notes cost no tokens); instructions are context not enforcement, use hooks or permissions to enforce. — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- Manus (18 July 2025): treat the file system as externalised memory; compress restorably (keep the URL or path, drop the content); keep errors in context; a rewritten todo.md recited each step counters goal drift over roughly 50 tool calls. — [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)

**ADRs and decision logs for agents**
- Duncan Davidson (O'Reilly Radar, 2 Oct 2026): ADRs in `docs/decisions` as markdown; status sets authority (accepted binds, proposed is context, superseded is history); each ADR holds only current text with git as changelog; superseded ADR gets `Superseded-On:` and the replacement carries `Supersedes:`; state each rule once in its owning ADR and cross-reference. Failure case: an agent kept an obsolete storage abstraction because an ADR still called it mandatory and layered a workaround instead of flagging the conflict; agents also over-document (clarifications become amendments). Fixes: AGENTS.md should say how agents apply and maintain ADRs, explicitly permit questioning ADRs that no longer fit, and require stop-and-propose on conflict. — [O'Reilly Radar](https://oreilly.com/radar/coding-agents-love-decision-records/)
- Vercel's adr-skill tells agents to look in `docs/adr/` before implementing, to propose a new ADR when making a decision such as a new dependency, and requires an implementation plan (files, patterns, tests, verification) inside the ADR. adr-kit adds "anti-rationalization" guards against skipping ADR writing. Single-source summaries; not independently verified. — [mcpservers.org adr-skill](https://mcpservers.org/agent-skills/vercel/ai/adr-skill)
- Microsoft hve-core keeps ADRs under `docs/planning/adrs/` with a separate frontmatter schema (tags, not keywords). — [hve-core docs](https://microsoft.github.io/hve-core/docs/contributing/documentation-maintenance)

**Session logs / work journals**
- Fulkerson's daily/weekly loops and "graduation" of validated patterns into CLAUDE.md rules or skills; Tuszynski's append-only `400-daily/YYYY-MM-DD.md` plus 34 lessons in MEMORY.md; Exbrain's append-only raw daily logs that a nightly compile converts into entities/decisions. — [Fulkerson](https://aaronfulkerson.com/2026/04/12/karpathys-pattern-for-an-llm-wiki-in-production/); [Cloud Codex](https://www.mpt.solutions/karpathys-llm-wiki-works-heres-what-broke-when-i-ran-it-at-real-scale/); [Exbrain](https://github.com/chaenmasahiro0425/exbrain)
- Karpathy-gist commenters describe a `.brain/` folder (index.md as current state, architecture.md, decisions.md, changelog.md, deployment.md, schema, pipeline) kept local and uncommitted, and a learning directory with a root progress.md and per-topic progress files updated at session end. — [gist comments](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)
- Manus-style recitation: the log is most useful when it is machine-parseable and short at the tail (the `grep "^## \[" | tail` pattern). — [gist](https://gist.githubusercontent.com/karpathy/442a6bf555914893e9891c11519de94f/raw)

**PARA**

**Spec / PRD folders**
- GitHub spec-kit: 149k stars, 13.4k forks; commands /speckit-constitution, -specify, -plan, -tasks, -implement, -converge, plus bug and assessment extensions; artifacts under `.specify/` (e.g. `.specify/bugs/<slug>/`, `.specify/assessments/<slug>/`); constitution created once per project; each step reviewed by hand; catalog extensions not audited. **Agent-instruction files as the schema layer**
- AGENTS.md: open plain-markdown "README for agents", stewarded by the Agentic AI Foundation (Linux Foundation), claims 60k+ open-source projects; nearest file in the tree wins in monorepos; explicit chat prompts override; no required fields. — [agents.md](https://agents.md)
- GitHub's analysis of 2,500+ repos (19 Nov 2025, updated 25 Nov): best files cover commands, testing, project structure, code style, git workflow, boundaries; commands early with flags; examples over prose; three-tier boundaries (always / ask first / never); start minimal and add detail when the agent errs. It is a pattern piece, not a controlled study. — [GitHub Blog](https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/)

### Inferences
- Memory Bank's fixed six-file template is a close cousin of the reader's per-project README / glossary / decisions set; its known weakness (an "active" file that goes stale) argues for keeping status out of per-project READMEs or dating it and letting the lint flag it.
- ADR guidance maps directly to the reader's `decisions.md`: add a status vocabulary (accepted/proposed/superseded), `Supersedes`/`Superseded-On` lines, "state each rule once, cross-reference elsewhere", and an explicit instruction in the schema file that agents must stop and flag when a task conflicts with an accepted decision, and may propose challenging one.
- pm-copilot-starter's "Authority" section (do alone / flag / only human) is an adoptable pattern for a shared layer where other people's agents write or propose changes.
- PARA is routing convenience, not a maintenance mechanism; the reader's one-folder-per-project plus Inbox already covers the routing and gains little from PARA.
- Spec-kit's constitution plus per-feature specs is worth borrowing only conceptually; it is code-centred and heavy.

- No reliable independent evaluations (benchmarks, user studies) of Memory Bank, PARA vaults or second-brain templates; all strengths and weaknesses are practitioner or vendor claims.
- Could not confirm Cline Memory Bank's GitHub star count or the current state of its docs beyond what the docs page showed.
- Spec-kit's file layout beyond `.specify/` was not confirmed (constitution/spec/plan/tasks file paths not shown on the fetched page).
- adr.github.io itself was not retrieved; ADR template details (MADR, Nygard) not covered.

## 3. What makes documentation usable by someone else's agent

### Takeaway
Evidence points to a small set of concrete conventions: a plain-markdown instruction file at the root (AGENTS.md, which Claude Code also reads via import), a short curated index (llms.txt style) with descriptions, self-contained pages with frontmatter (name and description that say what it is and when to use it), one-level-deep references, consistent terminology, and optionally an MCP server or skill packaging for discovery. llms.txt has weak measured crawler uptake but is read by coding agents pointed at docs.

### Cited Findings
- llms.txt spec (proposed 3 Sept 2024 by Jeremy Howard, spec modified 10 Aug 2026): markdown file with a required H1, a blockquote summary, optional detail sections, H2 "file list" sections of `[name](url): notes` items, and a conventional "Optional" section agents can skip; may sit at any subpath such as `/docs/llms.txt` and the most specific file wins; pages should have a markdown version at the same URL (`page.md`); discovery via `rel="alternate" type="text/markdown"` and `rel="describedby"`. Page says thousands of sites publish one and that OpenAI, Anthropic and Gemini publish llms.txt for developer docs. — [llmstxt.org](https://llmstxt.org)
- Measured uptake is weak for AI search: Ahrefs (137K domains, May 2026) found 28% publish one and 97% of files get zero requests; Otterly 90-day logs saw 84 of 62,100 AI bot visits touch it (about 0.1%); SE Ranking (about 300K domains) found no clear citation effect; Google says it does not use llms.txt for Search. Coding assistants (Cursor, Windsurf, Claude Code, Copilot) are the clearest consumers when pointed at a docs site. These are vendor/SEO studies, not peer-reviewed; the Something Inc. figures are a secondary write-up. — [Ahrefs](https://ahrefs.com/blog/llmstxt-study/); [Optimizely summary](https://www.optimizely.com/field-notes/articles/does-llms-txt-work/)
- Mintlify describes three layers: llms.txt as a directory of pages with descriptions (also hosts llms-full.txt), skill.md as a capability summary (what an agent can do with the product, inputs, constraints), and an MCP server through which agents query live docs and discover skills as MCP resources. Skills follow the agentskills.io spec, have `name` and `description` frontmatter, and can be discovered via `/.well-known/skills/index.json` with sha256 digests. Group-restricted skills are only exposed to authenticated users in matching groups. Mintlify's `mint score` tool checks llms.txt, llms-full.txt, skill.md and MCP discoverability. — [Mintlify docs](https://www.mintlify.com/docs/ai/skillmd.md)
- Agent Skills spec (agentskills.io): skill dir with required SKILL.md (frontmatter `name` max 64 chars lowercase-hyphen matching directory, `description` max 1024 chars stating what and when), optional scripts/, references/, assets/; progressive disclosure tiers: metadata about 100 tokens loaded at startup, instructions under 5000 tokens when activated, resources on demand; keep SKILL.md under 500 lines; file references one level deep; validate with `skills-ref validate`. — [agentskills.io specification](https://agentskills.io/specification)
- Anthropic skill authoring guidance: concise ("context window is a public good"); third-person descriptions with trigger terms; avoid deeply nested references because Claude may only `head` partially read nested files; add a table of contents to reference files over 100 lines; consistent terminology; avoid time-sensitive statements, put deprecated material in an "old patterns" section; descriptive file names (`form_validation_rules.md`, not `doc2.md`); prefer validator scripts and feedback loops; build evaluations first, test with each model you will use; develop with one Claude author and a fresh Claude tester. — [Anthropic skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Claude Code reads AGENTS.md as project instructions when no CLAUDE.md exists, and a CLAUDE.md can import AGENTS.md (`@AGENTS.md`), so one file can serve several agent products. Imports resolve relative to the importing file, max four hops. — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- GitHub's AGENTS.md study: specific commands with flags, code examples over prose, explicit boundaries, concrete stack versions; a docs-focused agent example has YAML frontmatter (name, description), a role, project knowledge, executable commands (e.g. markdownlint) and boundaries "never touch src/". — [GitHub Blog](https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/)
- Frontmatter conventions in the wild: Microsoft hve-core requires `title`, `description`, `author`, `ms.date` (YYYY-MM-DD), `ms.topic` (one of seven: overview, concept, tutorial, reference, how-to, troubleshooting, architecture), `keywords`, enforced by `npm run lint:frontmatter`; claude-obsidian requires type, title, status, created, updated, tags; Fulkerson tags provenance (human / LLM / LLM reviewed). — [hve-core](https://microsoft.github.io/hve-core/docs/contributing/documentation-maintenance); [claude-obsidian WIKI.md](https://github.com/AgriciDaniel/claude-obsidian/blob/main/WIKI.md); [Fulkerson](https://aaronfulkerson.com/2026/04/12/karpathys-pattern-for-an-llm-wiki-in-production/)
- Page-type templates: Astro-Han supplies fixed templates (raw, article, archive, index) in references/; the Karpathy gist and Exbrain both put an INDEX.md at the root as the "front door" so the agent scans one file instead of searching. — [Astro-Han skill](https://github.com/Astro-Han/karpathy-llm-wiki/blob/main/SKILL.md); [Exbrain](https://github.com/chaenmasahiro0425/exbrain)
- Link conventions: Astro-Han uses standard markdown relative links inside the wiki (file-relative) and root-relative paths in conversation; claude-obsidian lint handles Obsidian wikilinks and flags ambiguous basenames, recommending path-qualified links. — [SKILL.md](https://github.com/Astro-Han/karpathy-llm-wiki/blob/main/SKILL.md); [wiki-lint](https://github.com/AgriciDaniel/claude-obsidian/blob/main/skills/wiki-lint/SKILL.md)
- Content that is "unreadable to humans without the schema" is a reported hazard of agent-written wikis. — [Cloud Codex](https://www.mpt.solutions/karpathys-llm-wiki-works-heres-what-broke-when-i-ran-it-at-real-scale/)
- Search layer above a certain size: qmd (BM25/vector/re-rank, CLI and MCP) from the gist; Tuszynski added pgvector (about 126k chunks) only when hot content passed about 100k tokens. — [gist](https://gist.githubusercontent.com/karpathy/442a6bf555914893e9891c11519de94f/raw); [Cloud Codex](https://www.mpt.solutions/karpathys-llm-wiki-works-heres-what-broke-when-i-ran-it-at-real-scale/)

### Inferences
- For a folder consumed by other people's agents the cheapest, best-supported package is: a root AGENTS.md written for a reader who has none of the author's context (what the folder is, how it is organised, how to find things, what not to assume), an index file with one-line descriptions, per-page frontmatter with a description that says what and when, and relative links. All of this works with no tooling, in any agent.
- llms.txt as such is aimed at published websites; for a private repo folder an `index.md` in the same format (H1, blockquote summary, H2 lists of links with notes) is an inexpensive way to reuse the convention, but expect no automatic discovery; the AGENTS.md should point to it.
- Packaging parts of the layer as Agent Skills (SKILL.md with a good `description`) is the one mechanism with a real cross-vendor spec and progressive-disclosure behaviour; a successor's agent will pick skills up from metadata alone. MCP over the folder is only worth it if the folder is outgrown or served to non-technical users.
- The reader's own existing practice (CLAUDE.md rules not allowed to cite only `design/`, self-contained handover) lines up with Anthropic's guidance on self-contained, short, consistent-terminology files; the main extra step is to make the shared layer free of the private instruction file's conventions (e.g. no references that only resolve in the private layer).

### Gaps
- No Anthropic or GitHub guidance specifically on documentation folders (non-code) for agents beyond skills, CLAUDE.md and AGENTS.md; GitHub's study is about agent-instruction files.
- Mintlify's published guidance is largely promotion of its own features; no neutral evidence on whether skill.md/MCP improves agent answers.
- Not verified: llms-full.txt semantics (the fetched pages did not describe it); whether Claude Code actively fetches llms.txt by default.

## 4. Keeping a knowledge base from drifting

### Takeaway
Reported working controls are layered: deterministic scripts (broken links, orphans, frontmatter, index consistency, retired-term search, quote/number grounding) run in hooks or cron, LLM judgment lint for contradictions and staleness on a weekly cadence, review dates in frontmatter with a threshold (Microsoft uses 90 days), code-or-source-change-based staleness for pages tied to sources, and human gates on facts and deletions. LLM-only lint is described as unreliable and instructions alone as forgettable, so enforcement goes into hooks and scripts.

### Cited Findings
- Weekly cadence wins: Tuszynski found weekly lint recovered most orphans and dead links that occasional lint missed; recommends adding drift check, weekly lint and a "done means reference text matches reality" migration rule at 30-40 pages. — [Cloud Codex](https://www.mpt.solutions/karpathys-llm-wiki-works-heres-what-broke-when-i-ran-it-at-real-scale/)
- Retired-term drift linter: a script that checks any retired/decommissioned term against every live file and flags live mentions, run pre-commit and on cron. — [Cloud Codex](https://www.mpt.solutions/karpathys-llm-wiki-works-heres-what-broke-when-i-ran-it-at-real-scale/)
- Source-verifiable citations: Astro-Han's `check_evidence.py` greps numbers, dates and quotes from articles in the raw files they link and reports missing Raw links or links escaping `raw/`; because raw is immutable "a verified article stays verified" and the whole wiki re-checks in seconds. — [SKILL.md](https://github.com/Astro-Han/karpathy-llm-wiki/blob/main/SKILL.md)
- claude-obsidian: source and claim ledgers in JSON with lint checking "ledger contract violations"; read-only lint separate from repair; SHA-256 of targets recorded before repair; never auto-fix. — [wiki-lint](https://github.com/AgriciDaniel/claude-obsidian/blob/main/skills/wiki-lint/SKILL.md)
- Exbrain: "source link required for every claim (the receipts principle)"; research pages carry an expiry date; weekly shell-only lint (no LLM) for broken links, duplicates, staleness, expired research, scheduled via launchd; nightly compile by a cheap model; premium model only for weekly synthesis. — [Exbrain](https://github.com/chaenmasahiro0425/exbrain)
- Microsoft hve-core: every file under docs/ carries `ms.date`; default staleness threshold 90 days; PR validation checks changed files only and fails on stale ones; weekly Monday scan opens at most one GitHub issue per stale file (labels documentation, stale-docs, automated, needs-triage) and comments instead of duplicating; contributors update the date whenever they review, even without edits; files with missing or malformed dates are silently skipped by the freshness check, so a separate frontmatter lint is needed; link validation is not part of the freshness system. — [hve-core docs](https://microsoft.github.io/hve-core/docs/contributing/documentation-maintenance)
- Source-change-based staleness: JarHC's setup uses a `last_reviewed` field and a script flagging pages whose source files have commits newer than the review date; codocia has pages declare the code paths they cover and a snapshot file recording reviewed state, but its docs say passing only shows the snapshot is current, not the prose accurate; docdecay reports age by last commit. Small projects, not standards. — [WebSearch result summaries: docs.rs/codocia, pypi.org/project/docdecay, hve-core](https://pypi.org/project/docdecay/)
- Anthropic's claude-code-action has been used for doc-drift review in CI by mapping code paths to docs (single write-up, understandingdata.com). — [Doc Drift Detection in CI](https://understandingdata.com/posts/doc-drift-detection-ci/)
- Contradiction handling choices: Astro-Han keeps both claims with Status: Disputed/Outdated blocks; rohitg00 proposes confidence decay and supersession links with human override but commenters object (decay hides explanatory history, floats are false precision, supersession fails when sources disagree so keep a "Disagreements & open questions" section). Davidson's ADR rule: superseded records get `Superseded-On:` and the replacement `Supersedes:`. — [SKILL.md](https://github.com/Astro-Han/karpathy-llm-wiki/blob/main/SKILL.md); [v2 gist](https://gist.github.com/rohitg00/2067ab416f7bbe447c1977edaaa681e2); [O'Reilly](https://oreilly.com/radar/coding-agents-love-decision-records/)
- Enforcement through hooks, not instructions: Fulkerson's email-send gate, post-compact re-injection, post-commit capture; Claude Code docs say CLAUDE.md is context not enforcement and a PreToolUse hook or permissions should enforce hard rules. — [Fulkerson](https://aaronfulkerson.com/2026/04/12/karpathys-pattern-for-an-llm-wiki-in-production/); [Claude Code docs](https://code.claude.com/docs/en/memory)
- Hallucinated links persist; concurrent writes have no locking; small local models writing via hooks silently corrupt a wiki, so a human write gate is recommended. — [Cloud Codex](https://www.mpt.solutions/karpathys-llm-wiki-works-heres-what-broke-when-i-ran-it-at-real-scale/); [v2 gist](https://gist.github.com/rohitg00/2067ab416f7bbe447c1977edaaa681e2)
- Falconer (vendor, 28 Apr 2026): continuous background health checks rather than quarterly audits, weekly review cadence for enterprise content, designate canonical documents per domain so conflicting sources are treated as supplementary, owners accept or reject proposed updates. — [Falconer guide](https://falconer.com/guides/enterprise-llm-wiki-karpathy/)

### Inferences
- The reader's lint skill is currently LLM-driven with a 28-day SessionStart nudge. The evidence argues for splitting it: (1) a deterministic script (path citations resolve, frontmatter present, index matches files, orphans, retired-term list, optionally quote/number grounding) that can run in a pre-commit or SessionStart hook with no LLM, and (2) the existing LLM pass for contradictions/staleness. Weekly cadence is better supported than 28 days for deterministic checks.
- A `last_reviewed` or `updated` frontmatter date plus a threshold gives the "staleness date" signal cheaply; the practice "update the date when you review, even with no edit" avoids false staleness. Add a check that missing dates are counted as failures (hve-core's silent-skip pitfall).
- Staleness for product/design docs is better tied to sources than to calendar: pages could list their source documents, task cards and design files and the lint can flag pages whose sources changed since review (codocia/JarHC idea), but there is no code to diff, so this would need a convention (e.g. source file mtimes or log entries).
- "Citations that can be verified" is the strongest-supported control and the reader already has half of it; extending to literal-value checks is an incremental upgrade, with the Astro-Han script as a reference design.

### Gaps
- No reliable data on how often LLM-judgment contradiction checks actually find real contradictions versus false positives.
- Nothing found specific to non-code (product/design) documentation staleness tied to external tools such as a design tool or a task tracker.
- Doc-drift-in-CI claims are from small tools and blog posts; no standard exists (confirmed by the search summary).
- Could not retrieve full text of understandingdata.com article beyond its title and search summary.

## 5. Private working layer versus shared/published layer, and handover to a successor or team

### Takeaway
Few sources address this directly. The clearest patterns are: split by who owns what (Fulkerson's work skills shared, personal skills private; Exbrain's one author per layer; pm-copilot-starter's private repo and Authority section), use gitignored local files for private overrides (CLAUDE.local.md, uncommitted `.brain/`), and treat handover as a checklist with an early start. No authoritative standard exists for handing a markdown knowledge base to a successor.

### Cited Findings
- Fulkerson: work skills (meeting prep, memos, CRM analytics, PM methodology) are packaged and distributed to teammates, personal skills (health, relationships) stay on his machine; both layers use the same framework with separate permission boundaries. — [Fulkerson](https://aaronfulkerson.com/2026/04/12/karpathys-pattern-for-an-llm-wiki-in-production/)
- Claude Code supports layered instructions: managed policy (org-wide), user `~/.claude/CLAUDE.md` and `~/.claude/rules/`, project `./CLAUDE.md` (team-shared via source control), and gitignored `CLAUDE.local.md` for personal project notes; rules can be shared across projects by symlink (external symlink targets need approval; network paths are not followed); managed CLAUDE.md is for guidance, enforcement belongs in managed settings. — [Claude Code docs](https://code.claude.com/docs/en/memory)
- Imports pointing outside the working directory trigger a one-time approval dialog "to protect you from files other people commit to a shared project"; user-scope files are trusted. Implication: a shared layer that other people's agents pull in will be treated as untrusted external content by Claude Code. — [Claude Code docs](https://code.claude.com/docs/en/memory)
- Karpathy gist: the wiki is a git repo, so history, branching and collaboration are free; a commenter asks how to share with a team and says their team uses RAG plus an MCP server; another keeps a `.brain/` folder uncommitted for private memory. — [gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) (comments)
- Falconer (vendor): personal wikis work because one motivated person curates; at team scale maintenance grows with headcount, nobody owns updates and the vault "goes stale within a quarter"; capture should come from shared work tools; designate canonical documents per domain; owners review proposed changes rather than the system editing canonical docs. The article does not address permissions. — [Falconer](https://falconer.com/guides/enterprise-llm-wiki-karpathy/)
- Exbrain's single-author-per-layer rule avoids sync conflicts by construction; identity layer is human-written only. — [Exbrain](https://github.com/chaenmasahiro0425/exbrain)
- pm-copilot-starter: keep the repo private because it holds customer conversations; CLAUDE.md Authority section lists what agents do alone, what they flag, what only the human does. — [README](https://github.com/albertcollell-qurrent/pm-copilot-starter)
- inkeep/open-knowledge: "no-code team sharing and auto-sync powered by git/GitHub", MCP and skills for LLM wikis. — [README](https://github.com/inkeep/open-knowledge)
- Mintlify: group-restricted skills exposed only to authenticated users in matching groups (public vs restricted skill visibility). — [Mintlify docs](https://www.mintlify.com/docs/ai/skillmd.md)
- Handover: search found tooling (AIWG knowledge-transfer flow with a signoff checklist under `.aiwg/knowledge/` and a transfer report; Handover MCP; context-handover skills) and a generic recommendation to start handoff documentation 2-4 weeks before the date, but "no single authoritative standard"; these are small tools and vendor pages. — [AIWG handoff checklist](https://app.unpkg.com/aiwg@2026.5.10/files/agentic/code/frameworks/sdlc-complete/flows/handoff-checklist-template.md); [Handover MCP](https://mcpservers.org/es/servers/44-pixels/handover-mcp)
- A KB-migration vendor article notes that only content moves automatically while custom answers and escalation rules must be rebuilt by hand (vendor-specific but a useful checklist lens: content, behaviour rules, tacit answers). — [MyAskAI](https://myaskai.com/blog/move-knowledge-base-to-new-ai-agent)
- Karpathy's gist ends with: Bush's Memex insight that the unsolved part was "who does the maintenance"; the LLM handles it. In a handover, the maintainer role itself changes hands, which the pattern does not address. — [gist](https://gist.githubusercontent.com/karpathy/442a6bf555914893e9891c11519de94f/raw)

### Inferences
- A defensible structure for the reader's planned shared layer: private working layer (current workspace with personal CLAUDE.md, memory, Inbox, log) and a derived shared folder with its own AGENTS.md, index, frontmatter and lint, generated or promoted from the private layer rather than edited in parallel (Exbrain's one-author-per-layer logic; Karpathy's raw vs wiki separation). Promotion should be an explicit operation (like ingest) with a check that no page depends on files that exist only in the private layer.
- The shared layer should state, for outside agents, what it is, what is authoritative, its review dates, and what the agent may do (read-only, propose changes via issue/comment, never edit canonical pages), borrowing pm-copilot-starter's Authority lists and Falconer's "owner accepts or rejects" model.
- Because Claude Code treats external imports as untrusted and prompts for approval, the shared layer should be consumable as a plain folder (open it as the working directory) rather than relying on @imports from another repo.
- For handover to a successor, the evidence suggests: start early; deliver the folder as self-contained (the reader's own rule); include a "how this is maintained" page covering the operations (ingest, lint, log, decision logging), the schema file, and the scripts; and include a short "known gaps and open questions" page (aligned with the "Disagreements & open questions" practice) so the successor knows what is uncertain. Maintenance ownership (who runs lint weekly) needs a named successor action because the pattern assumes a single curator.

### Gaps
- No reliable source on handing over an LLM-maintained wiki specifically to a successor; the AIWG/Handover MCP items are tool docs, not experience reports.
- No evidence found on permission models for letting third-party agents write to a shared markdown KB; Falconer does not cover it.
- No data on whether outside agents actually follow an AGENTS.md placed inside a docs subfolder as opposed to the repo root; Claude Code documentation states nearest-file precedence only for AGENTS.md as defined by agents.md, and reading behaviour varies by tool.
- Nothing found on published/shared "views" of a private KB with redaction (e.g. stripping private notes) beyond ad hoc gitignore practice.
