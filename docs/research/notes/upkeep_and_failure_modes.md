# Upkeep and failure modes of personal agent setups (skills, rules, hooks, scheduled routines), as of 10 November 2026

Scope note: research done 10 November 2026 with gh (authenticated, read-only), official Claude Code docs (code.claude.com), Anthropic and practitioner posts, and Hacker News. Star counts and last-push dates were read from the GitHub API on that day. Where a claim comes from a secondary summary rather than the primary page, it is marked. Em-dash and acute-accent characters are deliberately avoided in this file.

## 1. How do people test that skills and rules actually trigger and are followed (evals, claude plugin eval, skill-doctor, pressure-testing with subagents, description tuning, regression checks)?

### Takeaway
Testing now has an official, cheap-to-adopt path: `claude plugin eval` (v2.1.269+, 11 Sep 2026) runs each case 3x with and 3x without the plugin and reports a delta, with a `tool_used: Skill` grader that measures triggering directly; skill-creator adds a train/test description-tuning loop. Superpowers adds a different layer, "TDD for skills" with subagent pressure scenarios, plus plain shell tests in CI for size and layout. `/skill-doctor` is a usage and cost report, not a quality test.

### Cited Findings
- `claude plugin eval` shipped in Claude Code v2.1.269 or later; requires Git 2.31+ if git is present. Run `claude plugin eval init` (Claude drafts cases and graders, asks what a good result is, proposes prompts that should AND should not trigger, trials them) then `claude plugin eval .` - [Test plugins with evals](https://code.claude.com/docs/en/plugin-evals.md)
- Each case runs 3 times by default; score = mean fraction of graders passed; a case passes at `--threshold` (default 1.0). Each case also runs 3 times with NO plugin (the baseline arm) and reports WITH, W/OUT and delta. "If a case scores 1.0 both with and without the plugin, the plugin isn't what made it pass." - [Test plugins with evals](https://code.claude.com/docs/en/plugin-evals.md)
- Cost model: roughly cases x runs agent runs with the plugin, the same again for the baseline, plus three short judge calls per `llm`/`baseline` grader per run. Every run is a real model call billed to the plan or API key - [Test plugins with evals](https://code.claude.com/docs/en/plugin-evals.md)
- Six grader types: `regex`, `tool_used`, `tool_order`, `file_exists` (free, computed from transcript/files), `llm` and `baseline` (judge-model calls). No custom-code graders. Recommended: one grader on the result and one on the steps taken (e.g. `tool_used`), and use `regex` over file contents for long output because `llm` graders vary more on longer text - [Test plugins with evals](https://code.claude.com/docs/en/plugin-evals.md)
- The skill-trigger grader is `type: tool_used, tool: Skill, input_match: '"skill"\s*:\s*"(?:[\w-]+:)?your-skill-name"'`. In a two-arm run these Skill graders are reported as indicators but excluded from the score (they cannot pass without the plugin); `arm: both` with `min: 0, max: 0` is the way to assert "must NOT invoke the skill" - [Test plugins with evals](https://code.claude.com/docs/en/plugin-evals.md)
- Doc's own diagnosis of the most common first finding: "a delta near zero with the case's `tool_used: Skill` grader failing, which means Claude isn't choosing your skill on natural phrasing. Adjust the skill's description, run again, and compare." Test prompts should be phrased as a user would type them, not naming the skill - [Test plugins with evals](https://code.claude.com/docs/en/plugin-evals.md)
- CI usage: `--json`, `--trust-plugin`, `--no-publish`, pin both `--model` and `--judge-model` "so a model rollout isn't mistaken for a plugin regression"; exit 0 = pass, 1 = a case below threshold or load/API errors, 143 = CI timeout; delta never changes the exit code; result JSON is versioned (`schemaVersion: 1`). `claude plugin eval init --bare <name>` for non-interactive scaffolding. If a `tool_used: Skill` grader passes but delta is negative, suspect the judge model first (re-run with `--judge-model sonnet`) - [Test plugins with evals](https://code.claude.com/docs/en/plugin-evals.md)
- Isolation: each run is a fresh non-interactive session with only the plugin loaded, in an empty working dir; Bash runs under the OS sandbox; hooks and real MCP servers run outside the sandbox, so scores are "advisory" for plugins with hooks you did not write unless run in a container/CI runner - [Test plugins with evals](https://code.claude.com/docs/en/plugin-evals.md)
- Docs position the two eval tools differently: skill-creator evals (`evals/evals.json`, subagent per case, blind A/B version comparison, description tuning, review viewer) for iterating on one skill in a conversation; `claude plugin eval` for plugins and CI. "Neither tool reads the other's case files." For a personal/project skill the no-skill baseline is `skillOverrides` set to `"off"`; for plugin skills use `claude plugin eval` - [Skills docs](https://code.claude.com/docs/en/skills.md)
- skill-creator description optimizer (Anthropic's `anthropics/skills`, 190,890 stars, last push 2026-11-06): generate 20 trigger queries (8-10 should-trigger, 8-10 should-not-trigger near-misses), split 60% train / 40% held-out test, run each query 3x, up to 5 iterations, pick `best_description` by TEST score to avoid overfitting. Says to make descriptions "a little pushy" because "Claude has a tendency to undertrigger skills". Warns simple one-step queries (e.g. "read this PDF") may not trigger a skill even with a perfect description because Claude handles them with basic tools, so eval queries must be substantive - [skill-creator SKILL.md](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md); stats via GitHub API (`gh api repos/anthropics/skills`)
- Superpowers (`obra/superpowers`, 315,123 stars, last push 2026-11-03, v7.0.2 on 2026-11-03): writing-skills states "NO SKILL WITHOUT A FAILING TEST FIRST", applies to edits too; method is RED (run a pressure scenario with a subagent WITHOUT the skill, record verbatim rationalizations), GREEN (write minimal skill, re-run), REFACTOR (close loopholes). Pressure types: time, sunk cost, authority, exhaustion, combined - [writing-skills SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-skills/SKILL.md)
- Superpowers micro-test rules for wording: one fresh-context sample per call, ALWAYS a no-guidance control ("if the control doesn't exhibit the failure, there is nothing to fix"), 5+ reps per variant, manually read every flagged match, and "Variance is a metric" (five different interpretations across five reps means the wording is not binding) - [writing-skills SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-skills/SKILL.md)
- Superpowers matches the form of the fix to the failure: prohibition + rationalization table for rules skipped under pressure; positive "recipe" for wrong output shape (prohibitions "trended worse than even the no-guidance control"); a REQUIRED template slot for omitted elements; and "No nuance clauses" (appending "unless it matters" degraded a winning recipe from consistent to noisy). It also says mechanical constraints enforceable by regex/validation should be automated, not documented - [writing-skills SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-skills/SKILL.md)
- Superpowers' description rule, found by testing: a description that summarizes the workflow makes the agent follow the description instead of reading the skill (a "code review between tasks" description caused ONE review instead of the two the skill specified). Descriptions must state only triggering conditions, start "Use when...", under ~500 chars if possible; getting-started skills under 150 words, frequently loaded under 200 words - [discovery.md](https://github.com/obra/superpowers/blob/main/skills/writing-skills/references/discovery.md)
- Superpowers repo `tests/` directory (read via gh): `skill-size` (shell test failing any SKILL.md at or above 20,000 bytes because Claude Code re-attaches only a truncated copy after compaction, issue #2481), `skill-layout` (keeps dev files out of skills; a 7.0.2 change moved pressure-test prompts out of a skill because "they installed next to SKILL.md and could be found by an agent mid-task"), `explicit-skill-requests` (headless runs with isolated HOME checking that the Skill tool is invoked for named skills), `claude-code`, `hooks`, `shell-lint`, `version-bump`, `diagnosing-superpowers` - [tests dir](https://github.com/obra/superpowers/tree/main/tests), [RELEASE-NOTES.md](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)
- Superpowers reports behavior changes with measured counts, e.g. v7.0.2 brainstorming: filler questions 41 to 23, reason-for-request elicited in 33 of 33 conversations (28 of 33 before), options-with-recommendation 8 of 8 runs vs bare "which one?" 8 of 8 before; blind-graded - [RELEASE-NOTES.md](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)
- `diagnosing-superpowers` is a skill that reads transcripts on disk after a bad session ("a skill that didn't fire" is a named trigger) and reports with `path:line` citations only; "No citation, no finding" - [diagnosing-superpowers SKILL.md](https://github.com/obra/superpowers/blob/main/skills/diagnosing-superpowers/SKILL.md)
- `/skill-doctor` (v2.1.252+): shows what each skill costs and how often it is used, flags skills in the listing that have never been invoked and says where to turn them off; report appears in the `/plugin` manager Stats tab, or as text with `-p`; not available over Remote Control - [Skills docs](https://code.claude.com/docs/en/skills.md)
- `claude plugin validate <path> [--strict] [--json]` finds SKILL.md files whose frontmatter does not parse (malformed YAML makes the skill load with empty metadata, so `/skill-name` works but Claude cannot match the description); v2.1.233+ for component dirs; also warns about a `CLAUDE.md` at the plugin root - [Plugin CLI reference](https://code.claude.com/docs/en/plugins/cli-reference.md), [Skills docs](https://code.claude.com/docs/en/skills.md)
- A third-party skill, `eval-skills` in FlorianBruniaux/claude-code-ultimate-guide (6,393 stars, pushed 2026-11-09), audits skills on eight criteria and "keeps structural validity separate from routing evidence" - [eval-skills SKILL.md](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/examples/skills/eval-skills/SKILL.md)
- diet103's showcase (10,053 stars, last push 2026-07-13) ships `verify-setup.sh`: eight checks including "firing a test prompt through the real activation hook", each with an exact fix command - [README](https://github.com/diet103/claude-code-infrastructure-showcase)
- Dedicated "claude code doctor" and "skill eval" GitHub repos are tiny: top "claude code doctor" hits have 4, 1, 1 stars; top "claude skills eval" hits have 0 to 1 stars (gh search, 2026-11-10). The official commands (`/doctor`, `/skill-doctor`, `claude plugin eval`, `claude plugin validate`) have displaced community tooling - gh search repos, 2026-11-10

### Inferences
- For a plugin-based kit the cheapest regression gate is: `claude plugin validate --strict` (free, seconds) on every edit, plus a small `claude plugin eval` suite of roughly 1 case per skill (1 should-trigger phrased naturally, 1 near-miss negative) run before releasing a version, with `--model`/`--judge-model` pinned. Budget: cases x 3 x 2 arms; use `--ablation none` while iterating.
- Treat the baseline delta as the keep-or-delete signal: a skill whose delta is ~0 with the model of the day is a pruning candidate (models improve; Anthropic's best-practices page says much old advice "was a workaround for something the model couldn't reliably do yet").
- The Superpowers "no-guidance control first" rule is the most transferable habit for /retro: before promoting a correction into a rule, check that the model actually still makes that mistake.
- Add a size test like Superpowers' (bytes of SKILL.md under compaction limits; the compaction re-attach cap in current docs is 5,000 tokens per skill and 25,000 tokens combined, so put the critical instructions at the top).

### Gaps
- No public measurements of how many skills/rules a typical personal setup keeps passing over time; no longitudinal data on eval-suite maintenance cost.
- `claude plugin eval` is two months old; no independent write-ups of its flakiness or judge-model drift were found beyond the docs' own cautions.
- I did not run any eval myself; all findings are from docs and repos.

## 2. What is known about skill triggering reliability and how to improve it (description wording, forced-eval hooks, SessionStart injection, limits on number of skills and description length)?

### Takeaway
Baseline triggering is unreliable (about 50% in sandboxed Sonnet 4.5 tests; 56% of Vercel's eval cases never invoked the skill), keyword-bearing prompts trigger near 100% while indirect ones near 0%, and a skill listing budget (1% of context window, 1,536-char per-entry cap) silently drops descriptions of least-used skills. Fixes with evidence: an explicit forced-evaluation hook (100% in the same sandbox tests), explicit instructions, always-in-context passive indexes, trimming descriptions and skill count; "MUST invoke first" wording can backfire.

### Cited Findings
- Scott Spence, sandboxed `claude -p` tests (Daytona sandboxes, Sonnet 4.5, 22 prompts per config, activation detected from `Skill()` tool_use events, dated 8 Feb 2026): no hook 55% and 50% (two runs), one-line echo hook 59% and 50%, forced-eval hook (bash script) 100% and 100%, LLM pre-classification hook (Haiku) 100% and 100%, native prompt-type hook 55% and 41%. Activation vs correct-selection rates were identical, so selection was never the failure point. Cost about $5.59 for ~250 invocations - [Measuring Claude Code Skill Activation With Sandboxed Evals](https://scottspence.com/posts/measuring-claude-code-skill-activation-with-sandboxed-evals)
- Same post, harder test (24 prompts, 5 with no matching skill, single run): forced-eval 75% overall with 5/5 true negatives; llm-eval 67% with 1/5 true negatives (4 false positives). Author recommends forced-eval; limitations stated: one model, single run for the harder test, 5 negative cases only - [same post](https://scottspence.com/posts/measuring-claude-code-skill-activation-with-sandboxed-evals)
- Baseline activation by prompt style (no hook): prompt containing the skill keyword about 100%; generic phrasing about 20-40%; indirect or conceptual phrasing about 0% - [same post](https://scottspence.com/posts/measuring-claude-code-skill-activation-with-sandboxed-evals)
- Earlier (16 Nov 2025) synthetic-API test on Haiku 4.5, 50 tests per hook: simple instruction hook 20%, LLM-eval 80%, forced-eval 84%; the post has a 13 Sep 2026 note saying later binary-based tests give different results. Author: "Your mileage may vary" - [How to Make Claude Code Skills Activate Reliably](https://scottspence.com/posts/how-to-make-claude-code-skills-activate-reliably)
- Search summary (secondary, treat as indicative) reports a separate write-up where a scoring-based pre-prompt hook lowered activation by up to 30 points in some configurations and the best result came from a directive skill description, not a hook - search result summary, unverified: [DEV Community](https://dev.to/lizechengnet/why-claude-code-skills-dont-trigger-and-how-to-fix-them-in-2026-o7h)
- Vercel eval (Jude Gao, 27 Jan 2026, Next.js 16 APIs not in training data; authors say eval count not stated and results may not generalize): baseline 53%, skill default 53% (worse than baseline on Test, 58% vs 63%), skill with explicit instructions 79%, AGENTS.md docs index 100%. "In 56% of eval cases, the skill was never invoked." Explicit instructions raised trigger rate to 95%+. Wording matters: "You MUST invoke the skill" made the agent read docs first and miss project context; "Explore project first, then invoke skill" did better. Docs index compressed 40KB to 8KB at the same 100% - [AGENTS.md outperforms skills in our agent evals](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)
- Anthropic's skill-creator says Claude "only consults skills for tasks it can't easily handle on its own", and that Claude undertriggers, hence "pushy" descriptions - [skill-creator SKILL.md](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)
- Official limits: `description` + `when_to_use` combined are truncated at 1,536 characters in the listing; "put the key use case first". If `description` is omitted the first non-empty body line is used. Angle brackets display as `&lt;`/`&gt;` - [Skills docs](https://code.claude.com/docs/en/skills.md)
- Official listing budget: "scales at 1% of the model's context window"; when it overflows Claude Code drops descriptions starting with the least-invoked skills; "The listing always contains every skill name". `/doctor` estimates listing cost and biggest contributors; `/skill-doctor` finds skills to turn off; overflow writes a warning to the debug log only (visible with `--debug`). Raise with `skillListingBudgetFraction` (e.g. 0.02) or `SLASH_COMMAND_TOOL_CHAR_BUDGET`; free budget with `skillOverrides: "name-only"` (names shown, descriptions hidden); cap configurable with `skillListingMaxDescChars` - [Skills docs, Troubleshooting](https://code.claude.com/docs/en/skills.md)
- Plugin skills are NOT affected by `skillOverrides`; manage those through `/plugin` - [Skills docs](https://code.claude.com/docs/en/skills.md)
- Community history of the budget (evolving, so versions matter): Jesse Vincent, 17 Dec 2025, Claude Code 2.0.70: default 15,000 characters (~4,000 tokens), "no warning" when exceeded, workaround `SLASH_COMMAND_TOOL_CHAR_BUDGET=30000`; Superpowers 4.0 was to merge infrequent skills and shorten descriptions - [blog.fsck.com](https://blog.fsck.com/2025/12/17/claude-code-skills-not-triggering). A secondary page (extracted from the 2.1.129 binary, May 2026) says the per-entry cap was 250 chars in v2.1.86, raised to 1,536 in v2.1.105 and the fraction setting arrived in 2.1.129 - [claudefa.st](https://claudefa.st/blog/guide/mechanics/skill-listing-budget) (secondary, unverified against changelog)
- GitHub issue anthropics/claude-code #64606 (opened 2026-06-02, now closed, v2.1.159, Opus 4.6): budget = context window x 4 bytes/token x 0.01 = 8,000 chars at 200k; projects with 25 skills (~490 chars each, 12,274 total) were at 153% of budget and 56 skills at 104%; Claude then "writes custom scripts instead of invoking available skills" and violated rules documented only in descriptions; four modes (fits, priority, truncate, names-only); no warning was shown. Reporter's asks: bigger default, visible warning, documentation. Docs now document the budget and the debug-log warning - [issue #64606](https://github.com/anthropics/claude-code/issues/64606)
- Issue anthropics/skills #881 (opened 2026-04-07, open): the `claude-api` skill's "DO NOT TRIGGER when" clauses were cut off by truncation, so negative conditions are lost first when descriptions are long - [issue #881](https://github.com/anthropics/skills/issues/881)
- Skill content lifecycle: once invoked, a skill's content stays in the conversation but is not re-read from the file; after compaction Claude Code keeps the first 5,000 tokens of each recently invoked skill, with a shared 25,000-token budget filled from the most recently used, so "older skills can be dropped entirely"; put the most important instructions at the top; "invoke the skill again to restore its full content" - [Skills docs](https://code.claude.com/docs/en/skills.md)
- diet103 showcase (10,053 stars): solves "skills don't activate automatically" with a UserPromptSubmit hook driven by `skill-rules.json` (keyword/intent/file-path triggers), a PreToolUse guard with a "two-try blocking model", and a PostToolUse tracker; "Born from 6 months" of use; ships an "MANDATORY SKILL ACTIVATION REQUIRED" message - [README](https://github.com/diet103/claude-code-infrastructure-showcase)
- Superpowers injects its bootstrap (`using-superpowers`, 492 words) through a SessionStart hook, and its release notes show how fragile injection is: a Pi extension turned the bootstrap off after the first prompt (and rewrote the prompt cache, 83% of first-to-second-prompt transitions per one reporter); OpenCode treated the word EXTREMELY_IMPORTANT in the first message as "bootstrap already present"; delegated subagents received the controller's bootstrap and some loaded `using-superpowers` instead of their task; the SessionStart hook spawned six child processes per start, costing tens of ms each on Git Bash - [RELEASE-NOTES.md v7.0.2](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)
- Hook context injection facts: `UserPromptSubmit` and `SessionStart` can return `additionalContext`, capped at 10,000 characters (more is saved to a file with a 2,000-char preview); the docs recommend factual phrasing over imperative "system" phrasing because the latter can trigger prompt-injection defenses - [Hooks reference](https://code.claude.com/docs/en/hooks.md)
- Anthropic's docs: if a skill rule "must hold every time", move it to a hook (a hook can live in the skill's `hooks` frontmatter and applies from invocation to session end); skill can be invoked manually with `/skill-name`; `disable-model-invocation: true` removes the description from context entirely and blocks Claude and scheduled tasks from invoking it - [Skills docs](https://code.claude.com/docs/en/skills.md)

### Inferences
- The two failure modes are different: (a) description never visible (budget/truncation), (b) visible but not chosen. Check (a) first with `/doctor` and `/context`; then tune (b) with trigger evals. Sandboxed numbers say hook-based forced evaluation fixes (b) at a latency cost of about 2 seconds per prompt (10.7 s vs 8.7 s mean in Spence's data).
- For a kit with few skills (<15), budget overflow is unlikely; the more likely cause of non-triggering is indirect user phrasing. Norwegian prompts are a specific risk: nothing found tests non-English trigger rates, so the kit's descriptions should carry Norwegian trigger phrases (the user's own skills already do this) and the eval suite should include Norwegian prompts.
- Keep each description to the key use case first, under ~500 characters, with the negative ("Do not use for...") conditions placed early because truncation drops the tail (issue #881).
- Rules that must apply to every response (banned characters) do not belong in a skill at all: skills trigger probabilistically, are not re-read, and can be dropped after compaction.
- A SessionStart bootstrap is a proven pattern (Superpowers) but needs its own tests (is it present after /clear, compaction, subagents?).

### Gaps
- No controlled measurement found for Claude Code 2.1.x with Opus-class models of skill activation vs number of skills or description length; Spence's tests are Sonnet 4.5 and Haiku 4.5 only. His Sept 2026 note says newer binary-based tests give different results, and I did not find those numbers.
- The 15,000-char, 8,000-char, and 1% numbers come from different versions; the official docs state only the 1% fraction and 1,536 cap.
- Reddit r/ClaudeAI and r/ClaudeCode were reachable only through aggregator snapshots; no thread with measured activation rates was found.

## 3. What health checks do people run on a setup (doctor commands, config audits, permission hygiene, duplicate skills, stale hooks) and how are they scheduled (log-driven nudge hooks, cron or scheduled agents, routines)?

### Takeaway
Claude Code now has built-in health checks: `claude doctor` (read-only, shell), `/doctor` (interactive, proposes fixes; covers unused extensions, invalid settings, duplicate subagent names, derivable CLAUDE.md content), `/doctor prompt-audit` (stale/conflicting instructions across CLAUDE.md, rules, skills, commands, agents), `/skill-doctor`, `/context`, `/hooks`, `/status`, `--safe-mode`. Scheduling options are cloud routines (1-hour minimum, fresh clone, no local files), Desktop scheduled tasks (local files), and session `/loop` (7-day expiry); no source found documenting a log-driven nudge hook pattern beyond the user's own.

### Cited Findings
- `/doctor`: "Setup checkup: installation health, invalid settings files, unused extensions, duplicate subagent names in the same directory, and checked-in CLAUDE.md content Claude can derive from the codebase, with proposed fixes." `claude doctor` from the shell prints read-only diagnostics without starting a session; `/doctor` inside a session proposes fixes and asks before applying - [Debug your configuration](https://code.claude.com/docs/en/debug-your-config.md)
- `/doctor prompt-audit [path]` (memory docs): Claude audits CLAUDE.md, CLAUDE.local.md, AGENTS.md plus rules, skills, commands, subagents and output styles under `.claude/` and `~/.claude/`, looking for "instructions written for older models, references to files or commands that don't exist, and files that contradict each other"; output is a report with proposed edits and "nothing in your files changes" until approved - [Memory docs](https://code.claude.com/docs/en/memory.md)
- Memory docs say periodically review CLAUDE.md, nested CLAUDE.md and `.claude/rules/` "to remove outdated or conflicting instructions"; "if two instructions contradict each other, Claude may pick one arbitrarily"; user-level and project rules conflicts: "Claude may follow either one" - [Memory docs](https://code.claude.com/docs/en/memory.md)
- Inspection commands: `/context` (everything in the window by category incl. skills, MCP tools, memory files; `/context all` in fullscreen), `/memory`, `/skills`, `/hooks`, `/mcp`, `/permissions`, `/status`, `/debug`; `claude --debug` shows hook matcher evaluation and exit codes; `claude --safe-mode` starts with CLAUDE.md, skills, plugins, hooks, MCP, commands, agents all disabled to bisect a problem; a deeper clean test uses `CLAUDE_CONFIG_DIR` pointing to an empty dir plus `--setting-sources user` - [Debug your configuration](https://code.claude.com/docs/en/debug-your-config.md)
- Silent hook failures documented by Anthropic: a `matcher` given as a JSON array is invalid (and under PreToolUse/PermissionRequest none of that file's other hooks load); lowercase `"bash"` matches nothing (case-sensitive); misspelled tool name "produces a matcher that matches nothing, so the hook fails silently"; comma separators did not work before v2.1.191; hooks belong in settings.json not `~/.claude.json`; hooks in a skill's frontmatter only appear after the skill is invoked - [Debug your configuration](https://code.claude.com/docs/en/debug-your-config.md)
- `onFailure: "block"` (v2.1.295+) on command/http hooks: a crashing, timing-out or invalid-output hook blocks the tool call or prompt instead of silently continuing; it has no effect on Stop and SubagentStop - [Hooks reference](https://code.claude.com/docs/en/hooks.md)
- Hooks reference lists an `InstructionsLoaded` event that fires when CLAUDE.md or `.claude/rules/*.md` is loaded (matchers session_start, nested_traversal, path_glob_match, include, compact); no decision control - useful for logging what actually loaded - [Hooks reference](https://code.claude.com/docs/en/hooks.md)
- Claude Code's own MEMORY.md auto-memory loads only the first 200 lines or 25KB; CLAUDE.md target "under 200 lines"; block-level HTML comments in CLAUDE.md are stripped before injection (free maintainer notes); `claudeMdExcludes` skips other CLAUDE.md files by glob - [Memory docs](https://code.claude.com/docs/en/memory.md)
- Duplicate/colliding skills: precedence enterprise over personal over project for same name; plugin skills are namespaced `/plugin:skill` so both load; project-root and nested skills both load; nested one prefixed. `/doctor` flags duplicate subagent names, not duplicate skills - [Skills docs](https://code.claude.com/docs/en/skills.md), [Debug your configuration](https://code.claude.com/docs/en/debug-your-config.md)
- Anthropic's official `claude-plugins-official` repo (46,629 stars, pushed 2026-11-09) ships `claude-md-management` (skill `claude-md-improver` for "periodic maintenance" aligning CLAUDE.md with the codebase, and `/revise-claude-md` to "capture session learnings" at end of session), `hookify` (create hook rules from explicit instructions or by analyzing conversation for behaviors you corrected; rule events bash/file/stop/prompt/all, regex plus conditions on fields like `new_text`, action warn or block), plus `session-report` and `skill-creator` - [plugin list via gh api](https://github.com/anthropics/claude-plugins-official/tree/main/plugins), [claude-md-management README](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/claude-md-management/README.md), [hookify README](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/hookify/README.md)
- Scheduling comparison (official): Cloud routines run on Anthropic infrastructure, need neither machine nor session, fresh clone only (no local files), minimum interval 1 hour, auto mode for prompts. ### Inferences
- A kit `/doctor` should mostly wrap what exists: call `claude doctor`, `claude plugin validate --strict`, `/skill-doctor -p`, and `/doctor prompt-audit`, then add only kit-specific checks the built-ins do not cover: hooks present and firing (test payload piped into each hook script, check exit code), the banned-character hook actually blocks a sample, version drift of the plugin vs the workspace template, skills in `~/.claude/skills` duplicating plugin skills, stale references in workspace CLAUDE.md to files that no longer exist, and the date of the last /retro.
- Make hook failures loud: use `onFailure: "block"` for PreToolUse/UserPromptSubmit hooks that enforce rules (silent continue is the default failure mode); for Stop hooks that cannot use it, add a doctor check.
- A log-driven SessionStart nudge (user's existing pattern) is cheap and survives machines/sessions; cloud routines cannot see local files, `/loop` expires in 7 days, and Desktop tasks need the machine on. For a fortnightly /retro and monthly /doctor, nudge-on-session-start is the more robust pattern for a laptop-bound solo user; a Desktop scheduled task is the only scheduler with local-file access if automation is wanted. No source in this research documents anyone running exactly that nudge pattern, so it is the user's own design, supported by the mechanics above.
- `InstructionsLoaded` hook plus a log line gives a cheap way to prove which rule files loaded in each session and feed /retro with real data.

## 4. What do experienced users say about over-engineering (too many skills or MCP servers, context cost of always-loaded instructions, ceremony, automation that silently rots); what do people delete; what minimal setups do respected practitioners recommend?

### Takeaway
Anthropic's own current guidance is minimal: CLAUDE.md under 200 lines, only what Claude cannot derive from the code, delete lines Claude already gets right, and "if you ever find yourself at forty [hooks], most are probably preferences". Research (ETH Zurich, Feb 2026) finds context files rarely help and add 20%+ cost, and IFScale shows instruction-following falling with density. Practitioners converge on: add a line only when you saw a failure, prefer scripts over MCP, throw away skills you do not need, and treat heavyweight frameworks skeptically.

### Cited Findings
- Anthropic best practices (current): CLAUDE.md "only holds what Claude couldn't work out from the code itself": commands to verify work, places where the code is misleading, decisions not in the repo, "Anything you've had to correct twice already". `/init` output: "the work is mostly removing lines"; memory guide says stay under 200 - [Best practices](https://code.claude.com/docs/en/best-practices.md)
- Same page: "If Claude keeps ignoring a line that is in CLAUDE.md, adding IMPORTANT probably won't fix it. Either the file has grown long enough that the line gets lost, or the line is a rule that can't have exceptions, in which case it belongs in a hook." And a "What you can stop doing" table: ALL CAPS emphasis "mostly makes Claude over-apply the rule"; "keep going / don't be lazy" lines "more likely to cause over-work"; describing architecture in CLAUDE.md ("Claude reads the repo itself"); `think hard` phrases; aggressive context management; subagents purely to save context. "If any other advice on this page ever starts to feel like busywork, that's probably a sign it belongs in this table too." - [Best practices](https://code.claude.com/docs/en/best-practices.md)
- Same page on hooks: "Whatever the scope, keep the enforced set small. Every hook and deny rule will occasionally fire when it shouldn't, and someone has to maintain each one. The 150-200 figure is the author's reading of the IFScale line of work, not a direct measurement on CLAUDE.md
- Anthropic engineering, "Effective context engineering" (29 Sep 2025): context rot, "attention budget", target "the smallest possible set of high-signal tokens", start with a minimal prompt and "add instructions based on observed failures", bloated tool sets are "one of the most common failure modes", "do the simplest thing that works" - [Anthropic engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Mitchell Hashimoto (5 Feb 2026): every AGENTS.md line traces to an observed bad behavior and "almost completely resolved them all"; fix by prompt line or by a small script - [mitchellh.com](https://mitchellh.com/writing/my-ai-adoption-journey)
- Armin Ronacher: prefers scripts and Makefile commands over adding MCP tools; uses essentially one MCP (Playwright) (2025 posts, summary secondary); "A Year Of Vibes" (22 Dec 2025): doubling down on skills, MCP "does not work for me", admits preferences are "vibes" - [lucumr.pocoo.org 2025/12/22](https://lucumr.pocoo.org/2025/12/22/a-year-of-vibes/). ### Inferences
- The consistent signal across Anthropic, Hashimoto, Cherny, HumanLayer and the ETH paper is evidence-gated growth: a rule exists because a failure was observed twice, and the file is audited for deletions as often as additions. For the kit's /retro this means each promoted correction should record the date and the observed failure, so a later /doctor can ask "does the model still make this mistake?" and delete rules that no longer earn their place.
- Biggest silent-rot risks in the evidence: skills dropped from the listing without warning, hooks with bad matchers that never fire, bootstrap injections that stop firing in subagents/after compaction, plugins and servers never invoked. Each has a concrete detector (`/doctor`, `/skill-doctor`, hook test payloads, `/context`).
- Ceremony cost is real mostly for multi-step process frameworks (Superpowers/GSD) on small tasks; the lightweight alternative practitioners cite is plan mode plus a short CLAUDE.md. For a kit whose users are designers/product people rather than developers, prefer a handful of narrow workflow skills over a methodology.
- A practical size target consistent with sources: workspace CLAUDE.md well under 200 lines (Anthropic) and ideally under 100 to 150 for the always-loaded layer including user-level, because the always-loaded instructions of user-level + workspace + rules + plugin bootstrap add together.

### Gaps
- No quantitative study of adherence vs number of rules in CLAUDE.md for agentic work was found; IFScale is a keyword benchmark and the "150-200" number is repeated by blogs, not measured on CLAUDE.md.
- No primary Reddit threads with concrete "what I deleted" lists could be retrieved (aggregator snapshots only). ## 5. How should deterministic enforcement (hooks, linters, scripts, CI) be split from instructions the model is asked to follow? Which rules only work as hooks (banned characters, formatting, commit rules)?

### Takeaway
Anthropic's rule: guidelines go in CLAUDE.md/skills (Claude may decide they do not apply), rules with zero exceptions go in hooks, deny rules or CI, and hooks that merely encode preferences should be deleted. Character-level constraints such as banned characters are a textbook hook case; the verified mechanisms are PreToolUse (inspect and deny file content before write) and Stop (read `last_assistant_message`, exit 2 forces another attempt, capped at eight consecutive blocks).

### Cited Findings
- Anthropic's two kinds of instruction: non-deterministic (prompt, CLAUDE.md, skills: "no guarantee that it'll follow") vs deterministic (hooks, deny rules, managed settings: Claude Code "has to execute this"). "If something has to happen every time, make it a hook, a deny rule, or a managed setting. CLAUDE.md is for guidelines, and Claude is allowed to decide a guideline doesn't apply." - [Best practices](https://code.claude.com/docs/en/best-practices.md)
- "A `prompt` or `agent` hook asks another model to decide, so it isn't deterministic either. For real enforcement, use a `command` or `http` hook", with `onFailure: "block"` if a crash should also stop the action - [Best practices](https://code.claude.com/docs/en/best-practices.md), [Hooks reference](https://code.claude.com/docs/en/hooks.md)
- Formatter rule as a PostToolUse hook after Edit/Write ("whether Claude remembers the rule no longer matters, because Claude isn't the one running it"); Stop hook for typecheck (exit 2 sends stderr back to Claude and it keeps working); the Stop block limit: after eight stops in a row with no tool call between them Claude Code overrides the next block and ends the turn; env `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` raises it - [Best practices](https://code.claude.com/docs/en/best-practices.md)
- Hooks reference: Stop and SubagentStop receive `last_assistant_message` (use it instead of reading the transcript, which "is written asynchronously and may lag"); on Stop, exit 2 "prevents Claude from stopping, continues the conversation"; PreToolUse receives `tool_name` and `tool_input` and can return `permissionDecision: deny` with a reason; PostToolUse cannot undo a finished tool call; `updatedToolOutput` rewrites tool results only (the hook-page excerpt did not document Write/Edit field names, so verify `content` for Write and `new_string` for Edit before relying on them) - [Hooks reference](https://code.claude.com/docs/en/hooks.md)
- Hook types: `command`, `http`, `mcp_tool` (deterministic), `prompt`, `agent` (model decides; `agent` experimental). Default timeout 600 s for command hooks, but 30 s for command hooks on UserPromptSubmit; SessionEnd hooks share a 1.5 s budget - [Hooks reference](https://code.claude.com/docs/en/hooks.md)
- Hooks do not enforce when run under `claude --bare` with hooks passed by `--settings`, and the Bash deny-rule `Bash(rm *)` does not block `/bin/rm` or `find -delete` because rules match the literal command string; Anthropic says use a PreToolUse hook or sandbox for a hard guarantee - [Best practices](https://code.claude.com/docs/en/best-practices.md), [Debug your configuration](https://code.claude.com/docs/en/debug-your-config.md)
- Auto mode is "a classifier model judging each action rather than a hard rule... so your 'never' rules belong in deny rules or hooks"; a conversational instruction like "don't push until I've reviewed" "can get lost when the conversation compacts" - [Best practices](https://code.claude.com/docs/en/best-practices.md)
- Skills docs: a rule that must hold every time can live in a hook in the skill's frontmatter, active from invocation to session end - [Skills docs](https://code.claude.com/docs/en/skills.md)
- Hookify (Anthropic official plugin) turns observed corrections into regex rules: `event: file` with `conditions` on `file_path`/`new_text`, `event: stop` for completion checks, `action: warn|block`, and `/hookify` with no arguments "analyzes recent conversation to find behaviors you've corrected" - [hookify README](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/hookify/README.md)
- Superpowers: "Mechanical constraints (if it's enforceable with regex/validation, automate it - save documentation for judgment calls)" is listed under "Don't create [a skill] for" - [writing-skills SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-skills/SKILL.md)
- HumanLayer: deterministic tools for style, "Never send an LLM to do a linter's job"; Stop hook runs formatter/linter and feeds errors back - [HumanLayer blog](https://www.humanlayer.dev/blog/writing-a-good-claude-md)
- Real-world instruction failure on a confidentiality rule: anthropics/claude-code issue #41852 (2026-04-01, closed) reports Claude suggesting posting confidential client details to a public repo "despite explicit rules" in CLAUDE.md prohibiting it; the user caught it - [issue #41852](https://github.com/anthropics/claude-code/issues/41852)
- Hook payload injection guidance: use factual phrasing for `additionalContext`; strings capped at 10,000 characters - [Hooks reference](https://code.claude.com/docs/en/hooks.md)
- Subagents: the built-in Explore and Plan agents skip CLAUDE.md at startup, so rules in CLAUDE.md do not reach them; custom subagents load it unless `omitClaudeMd`; hooks are the mechanism that still applies - [Debug your configuration](https://code.claude.com/docs/en/debug-your-config.md)
- Superpowers/Anthropic both warn emphasis does not substitute: Superpowers "No nuance clauses", Anthropic "piling on emphasis mostly makes Claude over-apply the rule" - [writing-skills](https://github.com/obra/superpowers/blob/main/skills/writing-skills/SKILL.md), [Best practices](https://code.claude.com/docs/en/best-practices.md)

### Inferences
- Rules from the user's list that must be hooks: (1) no acute-accent e in Norwegian output and files, (2) no em-dash, (3) commit-message format and the log.md line before commit, (4) never delete/overwrite Media/Archive/Tull, (5) block client-confidential strings from entering the reusable layer (a pre-commit scan). Rules that should stay instructions: tone, response shape, "ask when terms are ambiguous", decision-proposal behaviors, Norwegian style beyond banned characters.
- Practical banned-character design (my inference from the documented mechanics, not from a source that did exactly this): a single Python script used in two places. (a) PreToolUse on Write/Edit/MultiEdit: scan the incoming text for U+00E9/U+00C9 and U+2014, exit 2 or deny with a message naming the fix ("write 'ide' not 'ide-with-accent'"). This is fully deterministic for file content. (b) Stop hook: scan `last_assistant_message`; exit 2 forces a rewrite; remember the cap of eight consecutive blocks and that the offending text may already have streamed to the screen, so (b) corrects the next attempt rather than preventing display. (c) Optional git pre-commit hook or CI lint as the backstop for content written by other tools (Bash heredocs, scripts), which PreToolUse on Write/Edit does not see unless Bash commands are also scanned.
- Sanity-check gotchas: matcher strings are case-sensitive and must be a string not an array; test hooks after each Claude Code upgrade; log each block to a file so /retro can count violations (a rising count means the instruction layer is failing, a zero count for months means the rule might be deletable or the hook broken, so doctor should inject a known-bad sample).
- Keep the enforced set small (Anthropic's "forty" warning); for the user's setup a handful of hooks (character ban, commit/log, protected folders, confidential-scan) is well below the threshold.
- Put hook scripts in the plugin (reusable across clients) but their configuration of which strings are banned for a given client in the workspace layer.

### Gaps
- No source found describing banned-character or em-dash enforcement via hooks specifically (searched explicitly; results were generic hook guides). The design above is an inference.
- Hooks reference excerpt read covered the first ~100,000 of ~290,000 characters; Stop `stop_hook_active` field and exact Write/Edit `tool_input` field names were not confirmed in what I read.
- No measurement found of how often models violate negative character constraints such as "never use X" in non-English output without a hook.

## 6. For a solo consultant moving between clients: how to separate personal preferences, reusable method and client-specific context, and keep client-confidential material out of the reusable layer?

### Takeaway
Anthropic's mechanisms give three layers (user-level `~/.claude`, project/workspace CLAUDE.md and rules, gitignored `CLAUDE.local.md`) plus plugins as a distributable reusable layer, but all memory files are advisory, so confidentiality has to rest on structure (client facts only in per-client directories, session started from the client directory, separate config directories if strict) and deterministic scanning, not on a rule in a file. The community material on consultant setups is thin and mostly secondary.

### Cited Findings
- Load order: CLAUDE.md and CLAUDE.local.md are loaded from the working directory and every directory above it, concatenated from the filesystem root down (closer ones read last); subdirectory files load on demand when Claude touches a file there; `claudeMdExcludes` can skip files; `CLAUDE.local.md` is for personal per-project preferences and should be gitignored; user rules in `~/.claude/rules/` apply to every project and conflicts with project rules are not resolved ("Claude may follow either one") - [Memory docs](https://code.claude.com/docs/en/memory.md)
- Settings scopes: user `~/.claude/settings.json` (all your projects), shared project `.claude/settings.json` (committed), project-local `.claude/settings.local.json` (yours only, kept out of git); lists such as `permissions.allow` merge across files; Claude Code writes approvals "Yes, and don't ask again" into the local file automatically - [Settings docs](https://code.claude.com/docs/en/settings.md)
- Anything in `~/.claude/CLAUDE.md` or `~/.claude/rules/` loads in every session on that machine, so client facts placed there reach every client engagement (follows from the load rules above) - [Memory docs](https://code.claude.com/docs/en/memory.md)
- Auto memory is per repository (shared across worktrees) and loaded every session (first 200 lines or 25KB), written by Claude from corrections; the memory docs say both memory systems are context, "not enforced configuration" - [Memory docs](https://code.claude.com/docs/en/memory.md)
- `claude plugin validate` warns about a `CLAUDE.md` at a plugin root (a plugin cannot ship always-on instructions that way); plugin skills are namespaced and not affected by `skillOverrides` - [Plugin CLI reference](https://code.claude.com/docs/en/plugins/cli-reference.md), [Skills docs](https://code.claude.com/docs/en/skills.md)
- Strict per-client isolation: set `CLAUDE_CONFIG_DIR` per client (e.g. `~/.claude-a`) via direnv `.envrc`; this separates account, history, trust permissions and MCP server lists; caveats: undocumented in Anthropic docs as of 2026-08-12 (docs issue #33430 open at the time), claude.ai connectors live in the account so are not separated, billing not separated, on macOS the login token sits in a shared Keychain, IDE integrations may ignore it, and do not copy the whole `~/.claude.json` (holds all clients' tokens). Anthropic's debug doc does reference `CLAUDE_CONFIG_DIR` for clean-config tests - [Isolate Claude Code Environments Across Clients](https://pasqualepillitteri.it/en/news/10775/claude-code-isolate-environments-multi-client) (secondary), [Debug your configuration](https://code.claude.com/docs/en/debug-your-config.md)
- Practitioner layout (single dev.to author, one-year undated, "survives real clients"): short root CLAUDE.md (~40 lines: identity, tone, guardrails), shared generic slash commands that read each project's CLAUDE.md ("the commands themselves are generic, the behavior is specific"), per-project CLAUDE.md for stack/quirks/do-not-touch, `skills/` as verbs and `context/` as nouns "so Claude doesn't treat reference data as instructions", `handoff/` notes; no described method for keeping confidential material out of the reusable layer - [dev.to](https://dev.to/lamingsrb/the-claude-code-folder-structure-that-survives-real-clients-5497)

### Inferences
- Layer mapping that follows from the documented mechanics: (1) personal preferences (language, style, banned characters, response shape) in the plugin's hooks and a short user-level `~/.claude/CLAUDE.md`, containing nothing client-derived; (2) reusable method (design-brief, lint, retro, doctor skills; hook scripts) in the plugin, generic and testable with `claude plugin eval`; (3) client context (glossary, org facts, project names, handover content) only inside the client workspace directory and its CLAUDE.md/rules, with `CLAUDE.local.md` for private bits; (4) the workspace template is a copy-in skeleton with placeholders, not a place client facts are ever written back to.
- Because the plugin is the layer that gets reused and possibly shared, add a deterministic leak check to /doctor or a pre-commit/CI step: a per-client denylist file kept in the client workspace (client names, internal hostnames, ticket prefixes) that scans the plugin repo and template before any commit or publish. This is my inference; the research found no off-the-shelf tool for it.
- Auto memory (per-repo, written by Claude) can drift client facts into files you did not review; /retro should review memory files and promote only generic lessons into the plugin, deleting client-specific ones to the client workspace.
- If strict isolation is required (NDA, separate billing), `CLAUDE_CONFIG_DIR` per client plus direnv is the only documented-in-practice separation, with the caveats above; on Windows the source describes a more manual setup and IDE extension may ignore it.

### Gaps
- No Anthropic guidance on multi-client or consultant setups; nothing found on keeping client-confidential material out of a reusable plugin beyond general principles. Sources on this topic are secondary blogs; the ones fetched (pasqualepillitteri.it, dev.to) have a single author each and one is undated.
- No evidence found on whether plugin caching or marketplace publishing could leak files outside the plugin directory in practice; the plugin docs on data persistence directories were not read.
- The "separate account for billing" point and the macOS Keychain claim come from one secondary source and were not verified against Anthropic documentation.
